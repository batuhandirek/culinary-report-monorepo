# The analyst

An admin asks anything about the stored data in plain words; an agent plans, queries the database read-only and answers in prose, and every step it took stays under its answer. Questions live in threads, so a follow-up reads the answers before it.

## Map

- Backend `modules/analyst` (imports `AuthModule` and `LLMModule` only; reads every other module's tables by raw SQL, writing none, as `overview` does):
  - Entities: `AnalystThread` (`analyst_threads`: `title` (the first question's words, mentions as labels, `titleOf`), `owner`, `lastMessageAt`, `usd` summed over its answers), `AnalystMessage` (`analyst_messages`: `thread`, `author` (an admin, or the system account for an answer), `status` queued | running | done | failed, `model` (the one that answered), `usd`, `usage` (tokens, steps, queries), `finishedAt`), `AnalystMessagePart` (`analyst_message_parts`: `message`, `position`, `data` jsonb, `streaming`). `data` is `AnalystPartData` from `sdk`: `text`, `mentions` (a question's resolved `@` rows), `plan` (steps with todo | doing | done | skipped), `query` (purpose, sql, `show`, title, chart, columns, rows, rowCount, truncated, error, durationMs), `lookup` (the `schema` and `find` tools), `error`.
  - `AnalystThreadService`: the one writer of threads, messages and parts, and the one emitter of their in-memory events (`events/*.event.ts`). `ask(userId, text, threadId?)` resolves the mentions, then in one transaction creates the thread (or checks a follow-up: 409 while an answer is queued or running), the question (text + mentions parts) and the answer (queued, the system account's), and queues `AnalystAnswerJob` with `sendJobWithEm`. `list`, `get`, `rename`, `remove` (cascades). The answer's side: `loadForAnswer`, `setStatus`, `addPart`, `updatePart`, `emitDelta`. `messageOutput` / `threadOutput` build the one shape HTTP and the socket share (by hand: the socket has no DTO to drop the author's other fields).
  - `AnalystAnswerService.answer(messageId)` (worker `AnalystAnswerWorker`, `@OnJob('analyst-answer')`, `retryLimit: 0`, `localConcurrency: 3`): only a `queued` answer is written; the thread's history (`util/history.ts`: `historyMessages`, the last `ANALYST_HISTORY_MESSAGES` (16), earlier answers with the queries they ran, today's date and the active cities with the new question, turns merged so they alternate) goes to `AnalystAgent` with the run's tools; usage and dollars (`answerUsd`) go on the message and the thread. Any error ends it `failed` with an `error` part. At boot, answers left `running` by a restart are failed ("Interrupted by a restart").
  - `AnalystRun` (`tools/analyst-run.ts`): one answer being written. Mastra's `onChunk` text deltas stream into a text part (created on the first delta, `emitDelta` after, stored whole when a tool is called or a step ends), so parts read narration, step, …, answer in the order they happened; every write goes through one promise queue. It holds the budgets (`ANALYST_MAX_QUERIES` 24, `ANALYST_MAX_LOOKUPS` 24) across failover attempts; steps are capped by the agent (`ANALYST_MAX_STEPS` 30), the whole answer by `ANALYST_TIMEOUT_MS` (10 min).
  - Tools (`defineTool`): `plan` (one plan part, rewritten), `schema` (tables with row estimates, or columns with types, foreign keys and enum values), `find` (names to ids/keys: brands, venues, topics, aspects, terms, creators, cities), `run_sql` (one query: a `query` part, the rows to the model as tab-separated text, at most `ANALYST_MODEL_ROWS` (100), cells cut at 300; `show` + `title` + `chart` for a result meant for the admin; a chart naming a missing column is dropped and the model told).
  - `AnalystReaderService`: the Postgres role `ANALYST_READER_ROLE` (`analyst_reader`) and its own `pg` pool logged in as it. At boot, as the app's user, `ensureRole` runs `readerRoleSql`: create the role if missing; no superuser, no createdb/createrole, no inheritance, no replication, no RLS bypass, connection limit 5, a new random password every boot (never stored); `default_transaction_read_only = on`, `statement_timeout`, an idle-in-transaction limit; every grant taken back, then `USAGE` on `public` and `SELECT` on every table there but `ANALYST_DENIED_TABLES`, nothing else. `read(setup, query)` opens `begin read only`, runs each statement over the extended protocol (`queryMode: 'extended'`: one statement each, Postgres refuses a second), rows as arrays with their type oids, then `discard all`. A role that can't be set up (an app user without the right) leaves the analyst running no query.
  - `AnalystSqlService`: `run` checks the query (`util/sql-guard.ts`, `checkSql`), then reads it through the reader: `statement_timeout` `ANALYST_STATEMENT_TIMEOUT_MS` (20 s), a cursor fetching `ANALYST_FETCH_ROWS` (501), `ANALYST_STORED_ROWS` (500) kept on the part, int8 and numeric made numbers (`tableOfArrays`). `schema`, `search` (the picker and `find`), `resolve` (mentions, each with a facts line naming its ids for the model): fixed queries of ours, on the app's connection.
  - `AnalystGateway` (namespace `analyst`, path `SOCKET_IO_PATH` = `/api/socket.io`, so the dev proxy and the production router pass it): the JWT from the handshake's `auth.token`, else the `accessToken` cookie, checked once at connect; admins only. Every socket joins `analyst-admins` (thread list updates); `subscribeThread` / `unsubscribeThread` join a thread's room. It forwards the in-memory events as `sdk`'s socket events.
  - `AdminAnalystController` (`/admin/analyst`): `GET /threads`, `GET /threads/:id`, `POST /questions`, `PATCH /threads/:id`, `DELETE /threads/:id`, `GET /mentions?q=&type=&cityId=` (each with the token it inserts).
  - `AnalystAgent` (`agents/analyst.agent.ts`): `freeText` (the answer is `res.text`, no structured output), `cacheConversation`, `paidFallback`, model `ANALYST_MODEL` = `anthropic/claude-sonnet-5-5` with `gpt-5.4` behind it. Its instructions are fixed (a domain primer of the tables, the counting rules, SQL habits, how to answer); the date, cities and mentions come in the messages.
- `sdk` (`packages/sdk/src/socketEvents/analyst.socket-event.ts`): payload types and the socket event classes both sides use.
- Frontend `routes/(admin)/admin/ask` (Market › Ask, after Explore): `+page.svelte` (threads left, the open thread `?thread=` right, the composer under it, example questions on an empty thread), `stores/AskStore.svelte.ts` (the socket and the state; joining a room re-reads the thread so nothing before the join is missed; deltas appended until the part's update), `components/`: `AskThreads`, `AskMessage` (a question with its mentions as chips linking their admin page; an answer as plan, folding steps (open while it works), the answer's markdown, the shown results, errors), `AskQuery` (a step: purpose, rows, time; opens on its SQL and rows), `AskResult` (a shown result: chart over table), `AskChart` (bar or line, one axis, series in herb green, grape, chili, beet: validated together), `AskTable`, `AskComposer` (the `@` picker: two letters after `@` search `GET /admin/analyst/mentions`; arrows, Enter or Tab pick; chips of what is named), `AskMarkdown` over `lib/markdown.ts` (`markdownHtml`: showdown, then every tag outside a short list unwrapped and every attribute dropped but a link's http(s) target).

## Rules

- **The analyst can only read, and the database enforces it, not the prompt or our checks.** A query the model writes runs as `analyst_reader`, logged in as it: it holds `SELECT` on the readable tables and no other right anywhere, so an insert, update, delete, DDL, a role switch (`set_config('role', …)`), a file read or another session's termination is refused by Postgres whatever the SQL (checked against dev Postgres on 2026-11-03, read-only switched off too). Around that: the read-only transaction and the role's read-only default, one statement per extended-protocol message, the time limit and the row cap. The guard in front (`checkSql`: one SELECT / WITH / VALUES / TABLE, write words, `ANALYST_DENIED_TABLES`, the `pgboss` schema, catalogs holding passwords, `ANALYST_DENIED_FUNCTIONS`, quoted names and `E'…'` escapes read as Postgres reads them) only turns the usual refusals into a sentence the model can act on. Never run the model's SQL on the app's connection.
- **What the reader may read is every `public` table but `ANALYST_DENIED_TABLES`** (people's accounts and sessions, codes, the newsletter list, brand members, notifications, migrations, the analyst's own tables), granted afresh at every boot, so a new table is readable from the boot after its migration. A new table holding people's data goes into `ANALYST_DENIED_TABLES` in the change that adds it: rows go to the model's provider.
- **The reader's password is new at every boot**, so one process owns the role; with several app processes, take it from the environment instead.
- **Claude first, paid outside `llmPaid`** (the user's call, 2026-11-03): the agent has `paidFallback` and a Claude-first choice; each answer is a question an admin asked by hand and its cost is stored on it (a two-query answer: ~$0.02 on Sonnet, 8 s). `LLM_AGENT_MODELS=analyst:anthropic/claude-opus-5-5` puts it on Opus. Never call it from a job, cron or backlog of its own.
- **An answer is never retried** (the job's `retryLimit: 0`): a retry would pay again and double its parts. A failed answer says why; the admin asks again.
- **One open answer per thread**: a follow-up is 409 until the answer is done or failed; the composer waits.
- **Parts are kept as they happened**, never rewritten after the answer ends; the page derives the answer (text after the last tool part), the steps (everything before) and the shown results (`show`).
- **Mentions are `@Type:ref`** (`util/mentions.ts`): types venue (or branch), brand, aspect, topic (or food), term (or wording), city, creator, post; the ref an id, or a topic's, aspect's or term's key, or a city's slug. They are resolved when asked and stored with the question, unknown ones `found: false` (the model is told to say so).
- **The system account** (`system@culinaryreport.com`, role `system`, no password) is created on first use by `UserService.getSystemUser`; answers are its messages.
- **A runtime import from `sdk` in the frontend goes through `sdk/src`** (its `dist` is CommonJS, which Vite can't give named exports from in dev); type-only imports may use `sdk`.
