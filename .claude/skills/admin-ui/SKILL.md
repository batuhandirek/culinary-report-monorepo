# Admin UI

English, dense, desktop-first. Backend admin routes are `admin.*.controller.ts` in each module, behind `RolesGuard`.

## Map

`constants/ADMIN_MENUS.ts` is the single source for the sidebar, breadcrumbs, titles, the ⌘K palette and each list page's description. `components/admin/`: `AdminListPage.svelte`, `AdminDetailTabs.svelte`, `AdminPanel.svelte` / `AdminFacts.svelte` (thin presets over `Panel` / `KeyValueList`), `admin-load.ts` (`loadRecord`), `admin-format.ts` (English dates, state badge colours), `construct-admin-breadcrumbs.ts`, `AdminRawJson`, `AdminSimilars`, `CategoryPickerField`, `orders/order-timeline.ts`, `categories/`. The blog editor is `routes/(admin)/admin/blog` (`domain-blog`). Dialogs under `dialogs/admin/`. Tables: `ui/components/paginated-data-table` (`PaginatedDataTable`; `expand` draws a row's details under it when the row is opened, mounted only while open so it may fetch, with `rowKey` keeping it open across refetches: the Digestion page; an `api` answering `hasMore` instead of `totalItems` is paged without a count, the footer saying "more on the next page": the Workflows runs).

## Rules

- **The admin is organised around the product's pillars, the brand first.** Sidebar: Today · *Market*: Brands, Social, Trends, Explore, Ask (`domain-analyst`), Cities · *Output*: Reports · *Operations*: Data, Digestion, Workflows, Money · *Content*: Blog, Instagram, Public reports · *People*: Users, Sessions · *System*: UI kit. A venue is a brand's branch and a prospect is a brand on the sales list, so neither has a menu entry or a list page of its own: `ADMIN_MENUS` entries take `also` paths (`/admin/venues` lives under Brands, `/admin/creators` under Social) for the active entry and the breadcrumbs (a branch reads Brands › brand › branch). A page belongs under its section's path (a topic is `/admin/trends/[key]`); a section with several lists of one pillar is one page with tabs, not a menu entry per list (Social at `/admin/posts`: Posts, Creators, Own accounts, To review); no redirects are kept for old URLs while nothing is released.
- **`/admin` is Today** (`GET /admin/overview` and `GET /admin/overview/today`, `domain-venues-and-reports`): first "Waiting on you", every count with the page where it is done (urgent, then our work, then worth a look); a number band (reports of the report month, the sales stages, Apify spend); follow-ups due, next prospects, the posts we couldn't place, the pipeline's last run. Something that needs an admin's hand gets a line there, not a new page. User counts stay on `/admin/users`, linked at the bottom.
- **A page that shows a month or a city keeps them in the URL** (`?month=`, `?cityId=`; the default — the report month, the first active city — stays out of it) and passes them to every tab (`AdminDetailTabs keeps`), so a link from Today, a refresh and a shared link agree.
- **A chain is shown as the brand, never as one of its branches**: the Brands list and the brand page header give its category (most branches'), an icon one of them has and its stars over all its places' reviews; place figures (busyness, tables, search ranks) appear per branch, with a branch picker (Signals), never labelled as "the report's" place.
- **Report templates live under Reports, a brand's report configurations on its Reports tab** (`domain-venues-and-reports`): `/admin/reports/templates` (a "Report templates" button in the Reports header; the default marked, "Make default", each template's reports through `/admin/reports?templateId=`), and the brand's Reports tab lists its configurations (name, inactive, the template it came from or Custom) with "Add a configuration" (a copy of a template, or custom). A report is built from one of them: each row's "Build <month>", or the brand header's "Build report" menu (a configuration, or every active one); the brand page loads the configurations once for both. A build, a Rebuild and "Analyse again" run in the background (`lib/report-runs.ts`: `followReportRun` polls the run while the button spins, `announceReportRun` says how it ended): done opens or reloads the report; waiting for an LLM account, failed, or still going after 20 minutes is a toast with an "Open run" button to `/admin/workflows/[id]`. Both editors (`/admin/reports/templates/[templateId]`, `/admin/brands/[brandId]/report-configs/[configId]`) share `components/admin/reports/ReportSectionsEditor.svelte`: the cover locked first, the appendix a checkbox at the end, the rest dragged or moved with the arrows, each kind's settings under its row, "Add a section", and a preview of a built report laid out as the draft. The Reports list shows each report's name and template, and filters by template.
- **The public pages about a city are published at `/admin/public-reports`, by hand** (Content › Public reports, one page with tabs; the city kept across tabs, the month or the quarter per tab): the **City month** tab (`?month=`) for `/<city>/<month>`: Build (stored data as it stands), the preview through the same `CityHighlightView` the public page draws, Publish (only once the month is over, undo on the toast), Unpublish, the share images, and the city's do-not-list beside it. The **Food trends** tab (`?tab=food-trends&quarter=`) for `/<city>/trends/<YYYY>-q<N>`: the same steps, plus "Pull searches", the paid anchored Google Trends pull, with its estimated cost on the panel and its state polled while it runs. The **Front page** tab (`?tab=front-page`) is the one that publishes itself (`domain-venues-and-reports`): what is live, when the next edition is due, "Build now" (queued; the page looks again every few seconds until the new one is there), every edition with Publish or Unpublish (undo on the toast), what the selected edition says line by line with how many lines fell back, and the newsletter's counts beside it. A new public page about a city is a tab here, not a button on a Market page.
- **Instagram posts are designed at `/admin/instagram`** (the gallery) and `/admin/instagram/[design]` (the studio: the form, the post drawn live at its true size, Download PNG, a carousel's slides zipped, the share sheet where the browser has one, the caption with Instagram's and the brand's limits). A design is a Svelte component whose props are the form: `components/admin/instagram/designs/<Name>.svelte` plus its `definePostDesign` entry in `designs/index.ts` (fields, sample defaults, formats, a carousel's `slides`), built from `designs/parts/` (`Canvas` sets the theme's `--c-*` colours, the gutter and a story's safe zones; `Stamp`, `Wordmark`, `Photo`). The PNG is drawn in the browser by `modern-screenshot` from an unscaled copy off screen, so any CSS the app has works, and photos are kept as downscaled data URLs so they need no CORS. **Fill from data** (`FillFromData.svelte`, each design's `fills` in `fills.ts`) reads a city's built month (`GET /admin/highlights`, the data the public `/<city>/<month>` draws: already positive-only and without the do-not-list) and writes the design's text, rows and a caption in the brand's pattern; it sets only what the data knows, so a row's photo and credit stay with the place of the same name, Google listing slogans are cut from names (`placeName`), and the toast offers the undo. It warns while the month is unpublished: a piece naming places goes out after an admin approved it, and the caption's link leads to that page. A new fill is a function there returning `{ values, caption }`, or `null` when the month has nothing for it. Drafts live in the browser's storage per design, nothing on the backend. Designs follow the `brand` skill's canvas rules (1080 wide, 72px gutter, 32px+ body, 24px+ stamps, two tilts, one bite). A later TikTok or other channel is a page beside it under Content.
- **The durable workflows are at `/admin/workflows`** (Operations, `durable-workflows`): tabs Runs (the default; filters status, workflow name, queue, schedule, city, tag `key:value` "Started by" (`parent`, a run id) and "Top-level runs only" (`rootsOnly`: no child runs, so a fan-out's thousand agent calls stay out of the list), all in the URL; a city is sugar for the tag `cityId:<id>`; looked at again every ten seconds), Queues (a queue's name opens its runs) and Schedules (the cron with `lib/cron-text.ts`'s words beside it, Trigger with a link to the run it started, Pause and Resume with the undo on the toast). A run is `/admin/workflows/[id]`: status, timings and tags, "What it started" (the runs above it as a "Started by" trail, and the tree under it drawn left to right with Svelte Flow, `[id]/components/RunTree.svelte`: a node per run with its status and time, a parent's many runs of one workflow one dashed node with their counts that opens them in the list (`?parent=&name=`), read once and again only on its Refresh button: a reload re-measures the nodes, so it never polls, and the nodes carry their fixed size so a refresh doesn't blink; the node type is `fold`, since Svelte Flow styles its own `group`), the input and output as `AdminRawJson`, the error, the steps in order with their stored results and child-run links, Cancel, Resume, Fork (pick a step, or "Fork from here" on a step) and, on a live run not already `high`, "Run first" (`POST /admin/workflows/:id/priority`: it and every live run under it pass the `normal` runs waiting); a live run is read again every four seconds. The runs table shows a run's priority among its tags only when it is not `normal`. Statuses' words and moves are `lib/workflow-status.ts`, their colours `workflowStatusVariant` in `admin-format.ts`.
- **Money is at `/admin/money`** (Operations; tabs, groupings and provider names in `constants/ADMIN_MONEY_TABS.ts`, figures in `lib/spend-format.ts`): LLM spend (`?from=&to=` as inclusive UTC days, sent with `to` as the day after; `?groupBy=`; this month by agent stays out of the URL; presets; grouped by day every day of the range is a row, with a bar of dollars or of calls while everything was free; an agent, purpose or city row opens the Calls tab filtered to it, a workflow row its run), Calls (the ledger's filters in the URL; a run id links to the run) and Apify credit (`?tab=credits`: the account read live from Apify on every load, `GET /admin/apify-credit`: what is left, the cycle's limit, used, our running runs' caps, the cycle's dates, "Read again"; the actor runs waiting for credit, each linked to its run, and "Wake them" after buying credit; nothing is typed in). Apify's per-run costs stay on the Data page; the LLM tabs are the ledger only.
- **Counts are a month's, never all-time**, and a change says on which month ("+3 on August"); a blank month is "—", and a page says when a blank means "not scraped" rather than "none".

- A list page is `AdminListPage` around a table view. Columns use the `date` / `badge` / `count` types and `rowHref`, rather than a `dayjs().format()`, a `Badge` component column or an "info" action. Pass the generated client method as `api` and any component as a column (both typed `never`-param on purpose: generated clients have an enum twin per endpoint). **Never an `html` column over user text** (titles, names): use a `link` column.
- A detail page loads through `loadRecord` (an unknown id is an admin 404 inside the frame), keeps its tab in the URL with `AdminDetailTabs` (one body for the live tab), and is built from `AdminPanel` / `AdminFacts`. A state's badge colour comes from `admin-format.ts` so list and detail agree.
- The admin layout calls `setUiLabels` for English fallback words; everything under `/admin/ui-kit/**` stays Turkish because it shows storefront components.
- **`/admin/ui-kit` is the component gallery only** (`design-system`): shared controls and blocks, one specimen per state, from inline sample data. There are no fixture pages for whole screens any more; a screen that needs data dev rarely has is reviewed in the running app with seeded data.
- Browser review tricks (mobile iframe frame, logged-out origin): memory `reference_browser_review_tricks`.
