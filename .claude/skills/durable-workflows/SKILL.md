# Durable workflows and money

Two modules, one concern: work that costs money or waits must survive a deploy, be seen while it runs, and be accounted for afterwards.

- `modules/durable-workflows`: DBOS (`@dbos-inc/dbos-sdk` 5.4) inside Nest. Global, like `PgBossModule`; inject `DurableWorkflowsService` anywhere.
- The LLM call ledger (`LlmCall`, `llm_calls`) lives in `modules/llm`, written by `LlmCallsService` only. LLM only: Apify's spend and credit are the Apify module's own (`apify_runs`, `ApifyService.credit`), and no common module stands between a provider and its account (the user's call, 2026-11-06: each module handles its own spend and credit; the LLM side's credits are still to design).

## Map

- `durable-workflows.module.ts`: `forRoot(overrides?, { minimal? })` (`minimal`: the engine alone, no admin controller and its auth dependencies, for a test module), imported once by `AppModule`. **The module is the engine only**: it imports no domain module, and every workflow lives with the module it serves (the LLM call in `modules/llm`, the actor run in `modules/apify`, the pipeline's operations in `modules/pipeline/<operation>/`), reaching the facade because the module is global. In `onModuleInit` (which Nest runs for a global module after every other module's, with every provider built): the scanner registers the decorated methods, `DBOS.setConfig` + `DBOS.launch()` (recovering the runs a restart cut short), the declared queues are registered (`onConflict: 'always_update'`, so a changed limit applies at the next boot), the schedules written (`WorkflowScannerService.applySchedules`). `beforeApplicationShutdown` drains running workflows 30 s in production, 2 s elsewhere, then lets go: the next process resumes them. **Never start a workflow from an `onModuleInit`** (DBOS is not launched yet); `onApplicationBootstrap` and later are fine.
- `config/durable-workflows.config.ts`: `DURABLE_WORKFLOWS_DISABLED` (nothing launches; decorated methods stay plain methods, `start` throws; the eval CLI sets it), `DBOS_APPLICATION_NAME` (default `munchwerk-<NODE_ENV>`: DBOS files workflows, queues and schedules per application, so a dev backend on a copy of the production database never resumes or dequeues production's runs), `DBOS_APPLICATION_VERSION` (pinned `v1`, stored as `<application name>-v1` because DBOS wants version names unique across the applications sharing a system database, a cloned production database included: DBOS only recovers its own version, so a pinned one resumes every pending run with the current code; bump it only when a workflow's step order changed in a way old runs can't follow, and fork or cancel those from the admin), `DBOS_SYSTEM_DATABASE_URL` (default: the app database; the tables live in the `dbos` schema), `DBOS_POOL_SIZE`, `DBOS_LOG_LEVEL`.
- `decorators/`: `@DurableWorkflow(options?)`, `@DurableStep(options?)`, `@DurableSchedule(name, cron, { tz?, queue?, backfill? })`. Metadata only: without the module's scan (a PGlite suite without `durable: true`) the methods are ordinary methods.
- `services/workflow-scanner.service.ts`: walks every provider, registers each decorated method with DBOS as a plain function bound to its instance under `ClassName/method` (DBOS finds it again by those names on dequeue and recovery), and replaces the instance's method with one calling the registered function (`this` is never the service: DBOS accepts only its own `ConfiguredInstance` there). `DurableRegistry` keeps the registrations; `applySchedules(enabled)` writes the `@DurableSchedule`s (create or replace) and deletes this application's schedules no decorator names; `enabled` off (`INGESTION_IS_DISABLED`) deletes them all.
- `services/durable-workflows.service.ts` (the facade, the only place that talks to DBOS): `step(name, fn, options?)` (checkpointed inside a workflow, plain outside), `sleep(ms)`, `recv(topic, seconds)`, `send(workflowId, message, topic?, idempotencyKey?)`, `setEvent` / `getEvent`, `start(service.method, args, options)` (background or on a queue; pass the method as the service holds it), `enqueue({ className, name }, args, options & { queue })` (by name, for a service the workflow depends on; with `dedupe` and `onDuplicate: 'return-existing'` it hands back the run already in flight under the key, so both callers get its result), `isLaunched()`, `inWorkflow()`, `workflowId()`, `stepId()`, and the management calls the admin API uses (`list`, `listQueued`, `get`, `steps`, `cancel`, `resume`, `fork`, `schedules`, `triggerSchedule`, `pauseSchedule`, `resumeSchedule`, `queues`). `StartOptions`: `queue`, `workflowId` (idempotent starts), `dedupe` + `onDuplicate` (one in flight per key on a queue, the durable `singletonKey`), `priority` (`'high' | 'normal' | 'low'`, see the priority rule), `delaySeconds`, `timeoutMs`, `attributes` (tags: `cityId`, `purpose`; `list({ attributes })` finds them).
- `services/durable-priority.service.ts` (`DurablePriorityService`, `constants/durable-priority.constant.ts`): each run's priority level and how it passes down. The scanner runs every workflow body inside `runAs(workflowId, body)`, which reads the run's level once (its `priority` attribute) into an async-local store; the facade's `priorityOf` reads it there, synchronously, so a fan-out's starts keep their order. `set(workflowId, level, { onlyRaise })` rewrites the run and every live run under it (`parent_workflow_id`, recursively; ENQUEUED, DELAYED, PENDING) and the in-memory level of the bodies running in this process. It reads and writes `dbos.workflow_status` on a small pool of its own, never through `DBOS.getWorkflowStatus` / `setWorkflowPriority`: inside a workflow those are recorded as steps, and a step added to a body shifts the positions of every run in flight.
- `queues/define-durable-queue.ts`: `defineDurableQueue(name, { workerConcurrency?, globalConcurrency?, rateLimit?: { limitPerPeriod, periodSec }, minPollingIntervalMs? })` in a module's `queues/*.queue.ts`; the module registers every declared queue after launch and deletes this application's queues no declaration names. **Queue, schedule and version names are written with the application's name in front** (`munchwerk-development.ingest`, `munchwerk-development.pipeline-ingest-hourly`, `munchwerk-development-v1`; `DurableWorkflowsService.qualifiedQueueName` / `qualifiedScheduleName`, the `declared…` inverses for the admin): DBOS wants each unique across the applications sharing a system database, and a dev database cloned from production carries production's. Code and the admin API only ever use the declared names.
- In `modules/llm` (registered and exported by `LLMModule`; a module that calls it imports `LLMModule`): `workflows/llm.workflow.ts` (`LlmWorkflows.generate(agentId, input, context, options)`, on the `llm` queue, `queues/llm.queue.ts`, `LLM_QUEUE_CONCURRENCY` 8 and `LLM_GENERATE_WORKFLOW` in `constants/llm-workflows.constant.ts`) and `services/durable-llm.service.ts` (`DurableLlmService.generate(agent, input, context?, { model })` → `{ object, text, model, usage, usd }`, the starter any caller uses): **every agent call made through it is a workflow of its own, and it always resolves**. The agent travels by id (`LlmModelsService.agent(id)`, agents register themselves at init) because a workflow's arguments are stored as JSON, and the caller's call context travels in the options so the ledger files the call right. Inside, one step per try: it asks `agent.availability()` first and calls only when an account can serve; when none can (every account out of its day, the provider blocked or switched off) it sleeps until `until` (the next 00:00 UTC for a daily limit; a minute at least, `MAX_LLM_WAIT_MS` (24 h) at most, with jitter) and tries again, as often as it takes. Only the call's own error (an answer that doesn't fit the schema) fails it. There are no modes: a caller that must not wait decides that at the workflow level. To a calling workflow the whole thing is one step; outside a workflow's body (no DBOS, or inside a caller's step) it is the plain call waiting on a timer. `DurableLlmService.as(agent)` is the agent with its calls made that way (`generate`, `start`), for code written against an agent's shape (`readPostClaims`). **A call no child can carry** (an agent given in-memory tools, a caller that reads Mastra's whole result: the report's agents) runs inline with the same wait: `whenServed(agent, () => call, { context?, model? })` tries the call and, on `NoModelError` or a provider's fatal error, waits for the roster's reset (`llmWaitMs`, the same bounds) and tries again, any other error the caller's; the closure builds its per-try state (a fresh timeout, a fresh `ToolRun`). Inside a step it waits on a timer and a restart runs the step again, so a workflow first calls `untilServed(agents, onWait?)` in its body: a step per check, a durable sleep until every agent can be served, each wait handed to `onWait` (`LlmWait`, then `null` once served) for a page to read through `setEvent` (`ReportBuildWorkflow`).
- **LLM accounts** (`modules/llm/accounts/`): one `*.llm-account.ts` per provider account (`defineLlmAccount({ id, provider, apiKey, limits, requestsPerMinute? })`, its key from its own `LLMConfig` variable: `OPENAI_KEY_PRIMARY`, `OPENAI_KEY_SECONDARY`, `OPENROUTER_AI_API_KEY`, `ANTHROPIC_API_KEY`), listed in `llm-accounts.ts` (`LLM_ACCOUNTS`; OpenAI's in the order they take turns, one OpenRouter and one Anthropic at most); an account without its key is left out. Limits are per UTC day: `requestsPerDay(n)` (OpenRouter: 1,000, and 20 a minute its calls are spaced to) and `tokensPerDay(n)` (input and output together), optionally `{ models }` to count and hold only those: exact `LlmModelId`s (`openai/gpt-5.4` never covers `openai/gpt-5.4-mini`), several in one limit sharing its pool, a model no limit names left unheld; so an account keeps one limit per model pool, as OpenAI's allowance has one for the mini models and one for the full (`openai-primary`: 8M on `gpt-5.4-mini`, 800K on `gpt-5.4`; `openai-secondary` 2M across both). `LlmAccountQuotas` (`services/llm-account-quotas.service.ts`, shared by `OpenAIAccountsService` and `LlmModelsService`) counts each account's day: a request as a call starts (every OpenRouter try, failed ones too), tokens once it answers; an account at a limit serves none of its models until the next 00:00 UTC, so the roster moves the call on and `availability` names that reset. The counts start from the ledger (`LlmCall.account`, `LlmCallsService.accountUsageSince`) at boot and are merged from it every 5 minutes (the higher count kept), so a restart or the eval CLI doesn't hand an account a fresh day. Only agent calls are held by limits. Classifiers and embeddings have accounts of their own, `typesafe.classifier-account.ts` (`DecisionModelsService`) and `openai.embedding-account.ts` (`EmbeddingsService`, on `OPENAI_KEY_PRIMARY`; no rotation): no limits, every call filed in the ledger under the account (embeddings at $0.13 a million tokens), so `/admin/llm/spend?groupBy=…` shows the use. Calls in flight when a limit is reached still finish, so a token limit is overshot by them: set it under the provider's own.
- `util/workflow-context.ts`: `currentWorkflowId()` / `inDurableWorkflow()` for code that must not depend on the module (the ledger).
- **A workflow's steps are `@DurableStep` methods of its class** where they are more than a line (`CreatorWatchWorkflow`: `plan`, `save tiktok`, `save instagram`, each `@DurableStep({ name })` so the run's step list reads as words): the scanner replaces the instance's method with the registered DBOS step, so `this.plan(...)` from the body is checkpointed and outside DBOS it is a plain call. A step's arguments are not stored, only its result (JSON), so it may take a `Date`; it loads what it needs by id. `durable.step(name, fn)` stays for one-liners.
- **A part with an actor run (or an agent call) of its own is a child workflow, its call from the body, its save a step**: a step can't start a workflow (DBOS throws; `runActor` then runs inline, off the `apify` queue and its credit wait), so a service whose work includes an actor run gives the workflow the pieces: the input as plain data, the actor run from the body, the save as a step. `CreatorWatchWorkflow.scrapeTiktok` / `scrapeInstagram` are that, each a `@DurableWorkflow` method of the class: a workflow method called from a workflow's body runs as its child (`/admin/workflows` shows it under its parent). They run one after the other: two saving at once could give one person two creators (a new account joins its twin on the other platform as it is saved). Their arguments are stored JSON, so times travel as ISO strings.
- **Actor runs are typed calls**: an `ActorCall` (`apify/actors/actor.ts`: the `defineActor` actor, its typed input, the cap, the purpose) is plain JSON-safe data a plan step returns (an atom's `*Call`: `TiktokProfilesCall`, `ReviewsCall`) or a service builds, and the workflow's body runs it with `runActorCall(this.apifyService, call)` (typed items back) or `runActorCallRef` (the run's record, `ActorRunRef`, never its items: an atom reads them in its save step with `ApifyService.storedItems`); or `startActorCall` (the child's handle, for a fan-out: every run started first, then `settleHandles`); functions over `ApifyService.runActorRef` / `startActorRef`, so a test's fake service (`FakeApify`) serves them, as `durableNow` does for the facade. The options may name the run's owner (`ownerWorkflowId`, see the actor-run rule) and the run's memory.
- **Atoms** (`pipeline/atoms/<name>/`, registered by `PipelineModule`): one typed provider call as a workflow of its own that every operation composes, with one save path. `PlacesWorkflow` (`pipeline/atoms/places/`, `places.run`) is the first: a caller describes the search (`PlacesSearch`: `grid` on `City.locationQuery` for the city list, lookups and brand names; `typed` as a guest types it for OSM gaps and profile addresses; `map` from a map centred on the city for the dish searches; `details` by place id) and how the places are saved (`VenueScrapeService.savePlaces`: `newPlaces` `none` / `food-in-city` / `all`, `openings`); the atom builds the actor's input in a step (`input`, the pure `util/places-input.ts`: the shared flags written once, `maxQuestions: 0` on every mode), runs the actor as a child on the `apify` queue (`runActorCallRef`; a map search in `MAP_SEARCH_MEMORY_MB`; every cap floored at the actor's `GOOGLE_PLACES_MIN_CAP_USD`) and saves in a step (`save places`) that reads the items from the run's row. Its result (`PlacesResult`) is ids and counts: `recordId`, `found`, `saved`, `byQuery` (per query, the place ids in Google's order; a map search's one query) and `venueIds` (place id → venue id of the places kept); a caller that needs more of an item reads the stored items by `recordId` in its own save step (`VenueBusynessService.saveSample`, `DishSearchService.saveSweep`, `VenueScrapeService.detailsSummary`). Started from an operation's body with `start(run)` (a handle, for a fan-out; it tags the run with the city and purpose for `/admin/workflows` and sets `owner` to the operation's run id) or `call(run)` (its result), never from a step. `ReviewsWorkflow` (`pipeline/atoms/reviews/`, `reviews.run`) is the second: a caller describes the fetch (`ReviewsFetch`: `since`, these places from a day; `newest`, each place's one newest review with its day, to tell a quiet place from one a cap never reached) with its cap and purpose (`ReviewsCall`, what a plan returns) and the operation's clock (`now`, ISO: the stamp on every stretch and snapshot it writes); the atom builds the input (the pure `util/reviews-input.ts`), runs the actor as a child (every cap floored at `GOOGLE_REVIEWS_MIN_CAP_USD`) and saves in a step (`save reviews`) through `ReviewService.saveReviews`; its result (`ReviewsResult`) is `recordId`, `found`, `saved`, `rated`, `returned` (the places that answered, in order), `capped` (the run spent `REVIEWS_CAP_REACHED_SHARE` of its cap) and a `newest` fetch's `upToDate` / `missed`. `callAll(calls, now)` starts a plan's runs first and awaits them in order, failing only once every run has settled (what the rest fetched is saved; the error names the failed run). An atom's lowest cap comes from the actor's file, where the actor's price lives too (`GOOGLE_PLACE_USD`, `GOOGLE_REVIEW_USD`), and the pure helpers that read a provider's results (`places-search.ts`: `citySearchUrl`, `nearCity`, `orderedPlaces`) live in the atom's `util/`. ## Rules

- **pg-boss stays for fire-and-forget side effects** (an e-mail, a notification, an index update; `apps/backend/CLAUDE.md` Events). **DBOS is for work with several steps that spends money or waits**: a reading pass, the backlog drain, a pipeline step, an LLM call that must wait for the allowance, an Apify run. Converting a pg-boss job: its `*.job.ts` + `*.worker.ts` + `*.cron.ts` become a `workflows/*.workflow.ts` class (`@DurableWorkflow()` methods), a `schedules/*.schedule.ts` class (`@DurableSchedule(name, cron)` methods, the durable `@OnCron`) and a `queues/*.queue.ts` constant; the service that used to `sendJob` calls `durable.enqueue(ref, args, { queue, dedupe, onDuplicate: 'return-existing' })` with the workflow's `{ className, name }` from a `constants/*-workflows.constant.ts` (the names must match the class and method; `enqueue` throws for an unregistered one).
- **A workflow is the orchestration, steps are where the world is touched, and anything that runs a variable number of steps or needs a queue, a dedupe key or its own retry is a child workflow.** Anything that calls a provider, reads the clock at random, or writes to the database goes inside `durable.step(...)` (or a `@DurableStep` method); the workflow body only decides from step results. On a resume the body runs again from the start with every finished step's stored result, so a database write outside a step happens twice (the backlog drain updates its `BacklogRun` row inside the batch step for that reason). Step results and workflow arguments are stored as JSON: ids, counts and small objects, never entities or agents. An enqueue or `start` is a workflow operation: never inside a step. **Never `Promise.all` over step chains**: DBOS identifies a step by its position in the workflow, so two chains of unknown length interleaving on one counter (two actor runs polling at once) break the replay; fan out by starting child workflows and awaiting their handles instead, each with its own counter. This is why an LLM call and an Apify run are workflows, not step helpers.
- **A workflow can only be started from a workflow's body or from plain code, never from inside a step.** So a service a workflow wraps in `durable.step(...)` can make no actor run (`ApifyService` refuses one asked for inside a step or outside DBOS: `ActorRunOutsideWorkflowError`) and makes its agent calls inline (`DurableLlmService` falls back to the plain call when `durable.isInStep()`, the step being its checkpoint; `whenServed` adds the wait for an account to such a call). To make a service's Apify or LLM calls children, the service is split into **plan → run → save**: a `plan…` method that reads the database and returns plain data (ids, handles, searches, a cap), the actor or agent call made from the workflow body with that data (`ApifyService.runActor`, `DurableLlmService.start`), and a `save…` / `record…` method that stores what came back. `AccountScrapeService.planMentionedProfiles` / `planFollowers` / `planTracked` + `saveInstagramProfiles` / `saveTiktokProfiles` (the profile atoms' saves), `AccountTwinService.planLookup` + `saveLookup`, `SocialScrapeService.planCityTikTok` / `planVenueSearch` + `saveTikTokSearch` and `planCityInstagram` + `saveInstagramHashtags`, `ProfilePlaceService.planAddressSearches` + `saveAddressSearch` and `planPlaceQuestions` + `recordPlaceAnswer` are the pattern, and every caller of the places atom is built that way (`VenueScrapeService.planLookups` + `recordLookups`, `OsmPlaceService.planLookups` + `saveLookups`, `DishSearchService.planSweep` + `saveSweep`, `BrandService.planBranchSearch` + `saveBranchSearch`, `VenueBusynessService.saveSample`) and of the reviews atom (`ReviewService.planReportMonth` / `planRecent` / `planSnapshot` / `planBackfill` + `saveReviews`, `RatingSnapshotService.plan`); a one-call composition is kept only while a caller outside a workflow needs it, else it goes (`searchAddresses`, `askPlaces`, `DishSearchService.sweep`, `OsmPlaceService.lookup` went with the places atom; `ReviewService.scrapeReportMonth`, `scrapeRecent`, `snapshotRatings`, `backfill` and `RatingSnapshotService.snapshot` with the reviews atom; `AccountScrapeService.scrape`, `scrapeInstagram`, `scrapeTiktok`, `fillFollowers`, `trackProfiles`, `readMentionedProfiles` and `AccountTwinService.lookup` with the profiles atom; `SocialScrapeService.scrapeCityTikTok`, `scrapeCityInstagram`, `scrapeVenueSocial` with the search atoms). A workflow's body never reads the clock or the database directly: `now` comes from a `clock` step (`durableNow`), every list from a plan step, so a replay sees the same values.
- **Fan-out**: start every child first, then await the results in order (`DurableLlmService.start` returns a handle; `durable.start` too), never `Promise.all` over step chains. `ReadMentionedProfilesWorkflow.week` asks the agent about every due profile that way.
- **An operation that needs another's work calls it; nothing waits for, polls or wakes another run** (the user's call, 2026-11-06: no central workflow, no ordering by the clock). A city's run of an operation for a period has one id (`operationRunId`), so its own schedule and every operation depending on it start the same run: the first to ask starts it, the others get its handle, a finished one hands back its stored result (`runOperation`). Each operation has its own queue, so a run awaiting a dependency never holds the dependency's slot; the dependencies form no cycle, and two operations whose cadences call each other's (the week's lookups call the week's brand scrapes, whose month calls the month's lookups) are two classes, or the imports cycle and Nest injects `undefined` (`LookupVenuesWorkflow`, `LookupVenuesWeekWorkflow`). A reading city run (`read-posts.city`, `match-mentions.city`, …) is started with `dedupe` the city id and `onDuplicate: 'return-existing'` (`matchCityNow`, `readReviewsOfCity`, `classifyPressOfCity`), each item under its own fixed id (matching's close calls are children of the city's run with DBOS's own ids instead: a mention is matched again later, and the city's dedupe already keeps one run of them in flight). A provider being out is each child's own durable wait (`DurableLlmService`, the Apify credit wait).
- **`@EnsureRequestContext()` goes under the durable decorator** (`@DurableWorkflow() @EnsureRequestContext() async run()`), as under `@OnJob`; the class injects `MikroORM` for it. The workflow's steps run inside the same context.
- **Decorated methods are plain in a suite without `durable: true`**, and `DurableWorkflowsService` is auto-mocked there (`useMocker`): a service calling `durable.step` must be given a passthrough (`{ step: (_n, fn) => fn(), inWorkflow: () => false }`) or guard with `isLaunched()` / `isInStep()` as `ApifyService.startActorRef` does. **DBOS cannot run on PGlite**: its background jobs hold a transaction on one pool client while querying through another (`lockedBackgroundJob`), and the PGlite socket bridge serializes every client into one session, so the engine deadlocks (every later connection times out). `createPgliteTestingModule({ durable: true })` therefore boots DBOS on `DBOS_TEST_DATABASE_URL` (a Postgres database of its own, created when missing; the dev Docker one: `postgresql://postgres:<DB_PASSWORD>@localhost:5441/munchwerk_dbos_test`) under an application name unique to the run, with the app's tables still on PGlite, and runs the init hooks; declare such a suite with `describeWithDbos` (`src/tests/testing-module.ts`), which skips it when the variable is unset, as `npm run backend:test` does by default. Run it by hand before changing the module.
- **Every Apify actor run is a workflow of its own** (`ApifyWorkflows.runActor(actorId, input, request)` in `apify/workflows/apify.workflow.ts`, on the `apify` queue, `apify/queues/apify.queue.ts`, `APIFY_QUEUE_CONCURRENCY` 4: the one choke point on the account's concurrent runs). With DBOS launched `ApifyService.runActor` enqueues it with `dedupe: <actorId>:<input hash>` and `onDuplicate: 'return-existing'`, so callers asking for the same actor and input while one runs share that run and its items, and awaits the result: one step to a calling workflow, a top-level run to a pg-boss worker. Inside: `check credit` (`ApifyService.creditCheck`: the account read live, our running runs' caps off, and the cycle's end; while that is short of the run's cap the run publishes `APIFY_CREDIT_WAIT_EVENT` (`ApifyCreditWait`: its cap, purpose, since, until) and sleeps in `durable.recv(APIFY_CREDIT_TOPIC)` until it is sent a message or Apify's cycle ends (plus `APIFY_CYCLE_GRACE_SECONDS`), then checks again; the sender is the credit refresher `ApifyCreditSchedule` (`apify-credit-check`, every quarter hour: first closes the rows no workflow will close, `settleOrphans` below, then lists the waiting runs from its body, `ApifyService.creditWaiters` through `durable.list` + `getEvent`: DBOS reads an event only from a workflow's body, never inside a step, and only when one waits reads the account and wakes those it covers, `wakeableWaiters`, the longest waiting first while their caps fit) or an admin's `POST /admin/apify-credit/wake` after buying credit; an account that can't be read lets a run go, Apify enforces the cap anyway; a waiting run holds its `apify` queue slot). **Waiting on something another part of the app can tell is `recv` with the deadline as its timeout, and the teller `send`s; never a sleep-and-poll loop.**, `start actor run` (re-attaches to the run this very step started before a crash, by `ApifyRun.workflowId` + `workflowStepId` + input hash), `poll actor run` + `sleep(APIFY_POLL_MS)` until a final status, `store actor run` (items, cost, status: the items go into the run's own row, `ApifyRun.items`, jsonb, lazy and hidden, and the step and the workflow return only `ActorRunRef` `{ recordId, itemCount }`; `ApifyService.runActor` reads the items back with `storedItems(recordId)` for its caller, so callers still get `T[]`). **Never let a step or workflow return bulk data**: DBOS stores every step result, every workflow result and, in a calling workflow, the child's result once more (`getResult` is checkpointed), and keeps them; store the bulk in Postgres once and return its id. Pruning old runs' items is task `prune-apify-run-items`. `startRun`, `pollRun`, `finishRun` and `remainingCreditUsd` on `ApifyService` are that workflow's steps and nothing else's. `runActor` is `runActorRef` (the record, `ActorRunRef`) plus `storedItems`; **a run's row names its owner** (`ApifyRun.ownerWorkflowId`: `options.ownerWorkflowId`, which an atom sets to its operation's run id, else the workflow calling `runActor`), and the Data page's spend per month sums `apify_runs` by it (`DataCoverageService.monthSpend`: a run whose `workflowId` or owner is one of the month's runs), since an atom's actor run is a child's child of the operation's run and would otherwise be lost. `startActorRef` is the same start handed back as the child's handle (a fan-out awaits its handles with `settleHandles`). **An actor run is only ever this child workflow** (2026-11-08): asked for inside a step, from plain code or with DBOS not launched, `runActorRef` / `startActorRef` throw `ActorRunOutsideWorkflowError`, so a caller plans its runs in a step and starts them from its body; a test fakes the service (`FakeApify`). There is no inline run in this process any more, so a run never re-attaches by a caller's step: a resumed caller re-attaches to its child by DBOS's deterministic id. During a shutdown (`processShutdown`, `apify/util/process-shutdown.ts`) a start Apify refused for memory is not tried again; DBOS hands the unfinished runs to the next process. **A row left RUNNING by a dead workflow is closed** (`ApifyService.settleOrphans`, by the credit refresher every quarter hour and once at boot, since the schedule is deleted where ingestion is off): a RUNNING `apify_runs` row whose workflow is not live in DBOS (none, `CANCELLED`, `ERROR`, `MAX_RECOVERY_ATTEMPTS_EXCEEDED`, gone) takes Apify's own outcome and cost with `Items not stored: …` as its error, one that never started is `FAILED`, and one Apify still runs is left until it ends. A live workflow's row (`PENDING`, `ENQUEUED`, `DELAYED`) is its own: a restart resumes the workflow from its last step, polling on. Without this the credit counts a dead run's whole cap as spent for good. Cancelling an actor-run workflow doesn't abort the actor on Apify: it runs to its end or its cap, then the settle closes its row.
- **The roster says when it serves again** (`LlmModelsService.availability(choice, { paidFallback })` → `{ available, until, reason }`, `BaseMastraAgent.availability(context)`): the earliest end of the choice's blocks (an account out of its day, back at 00:00 UTC; an OpenAI refusal; OpenRouter's reset; Anthropic's block); `until: null` means nothing configured, disabled or paid outside `llmPaid`, and a waiting call checks again after `MAX_LLM_WAIT_MS`. The providers' refusals are in memory (the daily counts are not: they come from the ledger), so after a restart a waiting workflow may try a refused account once more.
- **Priority passes down** (the user's call, 2026-11-08: an urgent run's Apify and LLM calls pass everything waiting). Every start through the facade carries a level: its own `priority`, else the level of the workflow starting it, else `normal`; so a `high` operation's dependencies, atoms, actor runs and agent calls are all `high` without anyone passing it on. Every queue hands out runs by DBOS's number, lower first (`DURABLE_PRIORITY_RANK`: `high` 1, `normal` 50, `low` 100; a run started outside the facade, a schedule's firing or a fork, has DBOS's 0 and is read as `normal` by its children), then oldest first. The level is also stored as the `priority` tag on every run, queued or not, since DBOS keeps its number only for a queued run and a child reads its parent's level from the tag (`attribute=priority:high` lists them). A `high` start handed a run already there (its `dedupe` key's or fixed id's: `runOperation`, `onDuplicate: 'return-existing'`) raises that run and everything live under it (`onlyRaise`), or the urgent caller would wait behind the queue anyway. A raise never takes a slot from a run holding one: an `apify` slot held by a long actor run or a credit wait stays held. `high` is for a run someone is waiting on: an admin's button (`brand-branch-search.brand`, the food-trends pull, the reflag pass); schedules stay `normal`.
- **Money is read from its source, never estimated twice.** Apify's spend per run is `apify_runs`, its account is Apify's own figure read live (never a stored copy: the user raises the limit or tops up mid-cycle, and a stored snapshot goes stale), the LLM providers' spend is `llm_calls` (0 on OpenAI's allowance and OpenRouter's free models; Claude and TypeSafe priced). Never hard-code a cycle's credit (`APIFY_MONTHLY_CREDIT_USD` is only the Today page's figure).
- **Every workflow run is visible**: `GET /admin/workflows` lists runs with their steps, arguments and results; a run that failed is `ERROR` with its message, one a restart gave up on `MAX_RECOVERY_ATTEMPTS_EXCEEDED`; `resume` runs either on from its last finished step, `fork(startStep)` makes a new run from a step. A pause outlives a restart (`applySchedules` updates a schedule's definition only, never its status). A fork runs on DBOS's `_dbos_internal_queue`, not the original's. DBOS's own CLI works too (`npx dbos workflow list` from `apps/backend`, with `DBOS_SYSTEM_DATABASE_URL`).
- **What runs as a workflow today**: every Apify actor run (`ApifyWorkflows.runActor`, queue `apify`), every agent call made through `DurableLlmService` (`LlmWorkflows.generate`, queue `llm`), the daily backlog drain (`LlmBacklogWorkflows.drain`, `llm-backlog`), the Apify credit refresher, the food-trends pull (`FoodTrendsPullWorkflow.pull`, queue `food-trends-pull`, one in flight per quarter: `startPull` → one Trends compare run per group as a child → `savePull`), the `places` atom (`places.run`, every Google Maps places call), the `reviews` atom (`reviews.run`, every Google review fetch), the `instagram-profiles` and `tiktok-profiles` atoms (`instagram-profiles.run`, `tiktok-profiles.run`, every profile run), the `tiktok-search` atom (`tiktok-search.run`) and the `instagram-hashtags` atom (`instagram-hashtags.run`), an admin's report build and "Analyse again" (`ReportBuildWorkflow`, `report-build` / `report-analyse` on the `reports` queue, started `high`: a durable wait until an LLM account can serve the report agents (`untilServed`), then `ReportService` in one step whose agent calls run inline through `whenServed`, since they carry in-memory tools), aspect discovery (`AspectDiscoveryWorkflow`, `aspect-discovery.run` over the cities, each an `aspect-discovery.city` child: plan step → one `AspectSuggestionAgent` child per group → create and refile steps; ## The worked example: a pipeline operation

**An operation is a folder of its own** (`pipeline/scrape-reviews/`: `workflows/`, `schedules/`, `queues/`, `constants/`; `agents/`, `util/`, `controllers/`, `dto/`, `tests/` when it has them), registered by `PipelineModule`. Its workflow class has a `@DurableWorkflow({ name: workflowName(operation, cadence) })` method per cadence taking `(cityId, period)`, whose body reads as the operation does: the dependencies called first (`await runOperation(this.durable, this.fillCompetitors.month, FILL_COMPETITORS_MONTH, cityId, month)`), then its steps, each a `@DurableStep({ name: PipelineStepEnum.X })` method that loads the city by id and makes one call to the owning module's service (`ReviewService.planReportMonth`, `BlogScrapeService.scrapeCity`); a step never queries or writes itself. The constants file declares the cadence's `OperationRun` (`{ operation, cadence, queue }`) and its cron (`MONTH_CRON`, `WEEK_CRON` in `pipeline/shared/constants/cadence.constant.ts`, or its own); the schedule class is only `startForCronCities` per cadence. A reading operation (`read-posts/`) is the per-item form: `readPost(postId)` under a fixed id (`read-posts.post-<postId>`), its body plan → agent calls (`DurableLlmService` children, a long post's parts started in order then awaited in order: `readPostClaims`'s reader `start`) → save, each save a step calling `MentionExtractionService`; `readCity(cityId)` lists the unread ids in a step, starts every item's run, awaits them in order. An operation whose actor runs should be children of their own composes an atom (`this.places.call({ cityId, search, maxCostUsd, purpose, save })` between a plan step and a save step: `LookupVenuesWorkflow`, `OsmPlacesWorkflow`, `RefreshVenueDetailsWorkflow`, `DemandSampleWorkflow`; a fan-out starts every run with `this.places.start` and awaits them with `settleHandles`: `DishSearchesWorkflow`; a plan's review runs through `this.reviews.callAll(plan.runs, now)`: `ScrapeReviewsWorkflow`, `ReviewWatchWorkflow`, `RatingSnapshotWorkflow` (then one `reviews.call` for the quiet venues' newest review); one run after another, each cap from the last's result, where the budget stops a sequence: `BackfillReviewsWorkflow`) a plan's two profile runs one after the other, `this.instagramProfiles.call({ ...plan.instagram, cityId, now, save })` then `this.tiktokProfiles.call(...)`, each skipped when the plan has no handles for it: `ScrapeAccountsWorkflow`, `AccountFollowersWorkflow`, `ProfileTrackWorkflow`, `FindOwnAccountsWorkflow` (with `save: { accounts: 'known' }`, then a `link twins` step reading the runs' stored items by their `recordId`s), `CreatorWatchWorkflow` (TikTok then Instagram), `ReadMentionedProfilesWorkflow` (Instagram alone); one `this.tiktokSearch.call({ ...plan, cityId })`: `ScrapeTiktokWorkflow`, `ScrapeVenueSocialWorkflow`; the month's posts and reels runs through `this.instagramHashtags.callEach(plan.calls, cityId)`: `ScrapeInstagramWorkflow`). **An actor with one caller is no atom but runs the same way**: its service is split into a plan (the `ActorCall`s as plain data, from a step) and a save (reading the stored items by `recordId`, in a step), and the operation's body starts the run as a child, `runActorCallRef` for one, `startActorCall` for each of several then `settleHandles` (a failed run's items are no one's; the save gets `null` for it and the body fails the run once the rest is saved): `ScrapeReviewsWorkflow` (TripAdvisor's page search, then its month: `TripadvisorReviewService.planPages` / `savePages`, `planMonth` / `saveMonth`), `ScrapeVenueSocialWorkflow` (the Instagram location actor: `SocialScrapeService.planVenuePlaces` / `saveVenuePlaces`), `ScrapeCommentsWorkflow` (one run per post in 1 GB each: `planComments` / `saveComments`), `PostCountsWorkflow` (TikTok's and Instagram's readers: `PostCountsService.plan` / `save`), `ScrapePressWorkflow` (Google News and Google: `WebMentionService.planMonth` / `saveMonth`), `ScrapeDeliveryWorkflow` (one Wolt run per restaurant, then Lieferando's listing on what is left: `VenueDeliveryService.planWolt` / `saveWolt`, `planLieferando` / `saveLieferando`), `SearchInterestWorkflow` (the topics' and the brands' Trends runs: `SearchInterestService.plan` / `save`), `DemandSampleWorkflow.reservations` (TheFork's run and OpenTable's per domain and date started first, Google's free pages fetched in a step meanwhile: `VenueReservationService.planSample` / `sampleGoogle` / `saveSamples`), and outside the pipeline `FoodTrendsPullWorkflow.pull` (one Trends compare run per group). No actor runs inside a step.
