# Recover pipeline runs and paid Apify results when the backend restarts mid-run

## Goal
A backend restart (deploy, crash, dev watcher) while a `PipelineRun` is executing leaves no run stuck in RUNNING, and items an Apify run already paid for are not thrown away: the run is marked failed with a clear error on boot, and its Apify run can be picked up again instead of paying twice.

## Why
`PipelineService.execute` holds the Apify run only in memory: `ApifyService.runActor` awaits `client.actor().call()`, and the `ApifyRun` row gets its `apifyRunId` only after `call` returns. A restart in between leaves both `pipeline_runs` and `apify_runs` in RUNNING forever, and the dataset Apify charged for is never read. On 2026-10-18 this cost $1.91 for nothing stored (runs `70e7a821…` and `80a4eb05…`, marked FAILED by hand). In production a deploy during the monthly run would do the same, and `retryLimit: 0` means nothing resumes it.

## Scope
- In: store `apifyRunId` as soon as the run starts (`client.actor().start()`, then wait with `client.run(id).waitForFinish()`), so the row always names the Apify run. On boot, mark RUNNING `PipelineRun`s FAILED (error says the backend restarted) and RUNNING `ApifyRun`s with an `apifyRunId` re-read from Apify (status, cost, item count).
- Out: resuming a pipeline step automatically (a retry may pay again; an admin reruns it). Re-using a finished Apify dataset in a rerun can be a follow-up.

## Acceptance
- [x] `ApifyRun.apifyRunId` is set before the run finishes (PGlite test with the Apify client mocked).
- [x] On boot, a RUNNING `PipelineRun` becomes FAILED with a "backend restarted" error; a RUNNING `ApifyRun` gets Apify's final status and cost (PGlite test).
- [ ] `/admin/pipeline` shows no run stuck in RUNNING after a restart.

## Log
- 2026-10-18: Seen again: `SEARCH_INTEREST` Berlin 2026-09 (run 63b68566) stuck RUNNING after the dev watcher restarted at 11:32 UTC; its Apify run iVweStMkTvrsMtwYp finished ($0.63) with nothing stored. A 30-minute step is likely to be cut by any edit during dev.
- 2026-10-18: Done, and went further than "mark failed": `ApifyService.runActor` now `start`s the run and stores `apifyRunId` before waiting (`waitForFinish`); each pipeline step runs inside `apifyRunContext` (pipeline run id + step key), and runs are tagged with it and an `inputHash`. On boot `PipelineRecoveryService` re-queues every RUNNING run (`resumes` + 1, up to `MAX_PIPELINE_RESUMES` = 5, then FAILED); `execute` skips the steps already in `result`, and the step it was in re-attaches to its own Apify runs with the same input (`earlierAttempt`), so nothing is paid twice. Apify runs no resumed step will re-attach to are settled from Apify (`settleOrphans`). Tests: `apify.service.pglite.spec.ts` (run id stored while running, context tags, re-attach, never another step/input/failed run, orphans), `pipeline-recovery.pglite.spec.ts`.
