# Make headless Chrome run in the production image so report PDFs work

## Goal
`GET /api/admin/reports/:id/pdf` returns a PDF in production as it does locally.

## Why
`ReportPdfService` prints the report with Puppeteer. Locally, `npm install` downloads Chrome into `~/.cache/puppeteer`. The nixpacks image has neither that cache at runtime nor the system libraries Chrome needs (nss, atk, cups, libdrm, gbm, pango, fonts), so the first PDF request will fail to launch the browser.

## Scope
- In: the Chrome binary and its libraries in `nixpacks.toml` (for example `nixPkgs = ["chromium", …]` plus `PUPPETEER_EXECUTABLE_PATH`, or keep Puppeteer's download with `PUPPETEER_CACHE_DIR` inside the app directory); a font with ★ and umlauts as a fallback; a smoke check after deploy.
- Out: moving PDF rendering to a separate service or queue.

## Pointers
- `apps/backend/src/modules/reports/services/report-pdf.service.ts` (launch args, `--no-sandbox`)
- `apps/frontend/src/routes/print/report/+page.svelte` (the page Chrome prints, at `PUBLIC_APP_URL`)
- `nixpacks.toml`

## Acceptance
- [ ] (Not verifiable here: no deploy. See the after-deploy check in the log.) On the deployed app, "Download PDF" on `/admin/reports/<id>` saves a multi-page A4 PDF with the oat page colour and the running footer.

None.

## Log
- 2026-10-17: Nixpacks' Node provider already reacts to `puppeteer` in package-lock.json: it adds apt libs plus apt `chromium`, which on its Ubuntu 24.04 base image is the snap transitional package and doesn't run in a container. Puppeteer's own download (Chrome for Testing 148.0.7778.97 for puppeteer 24.43.1, both `chrome` and `chrome-headless-shell`) runs in `npm ci`'s postinstall. Chosen: keep Puppeteer's download (version-matched to the library; nixpkgs' chromium follows the nixpacks archive pin, not Puppeteer) with `PUPPETEER_CACHE_DIR=/app/.cache/puppeteer` in `[variables]` (nixpacks emits it as ARG+ENV, so install and runtime agree), and an explicit `aptPkgs` list without `"..."` (replaces the provider's, dropping apt `chromium`). Fonts: `fonts-dejavu-core` (★, umlauts, ß) and `fonts-noto-color-emoji` behind the app's Onest web font. Stars in the report are SVG (`Stars.svelte`) anyway.
- 2026-10-17: `ReportPdfService` launch: added `--disable-dev-shm-usage` (a container's /dev/shm is 64 MB). Puppeteer itself reads `PUPPETEER_EXECUTABLE_PATH` and `PUPPETEER_CACHE_DIR`, so no code reads them. `nixpacks` isn't installed locally (not installed, per the rules), so no `nixpacks plan`; the toml parses (tomllib).
- 2026-10-17: Local check: `ubuntu:noble` amd64 container, `apt-get install --no-install-recommends` of exactly the aptPkgs list (as nixpacks does) + nodejs, `PUPPETEER_CACHE_DIR=/app/.cache/puppeteer npm i puppeteer@24.43.1`, launch with the service's args, `page.pdf` of "Café Zimtschnecke ★★★★☆ — Brücke, Grüße, Öl, ß 🥞": Chrome 148 launched, PDF embeds DejaVuSans and NotoColorEmoji, pdftotext reads the stars and umlauts back. Not checked: the real nixpacks image (node from nix, `nixLibs` LD_LIBRARY_PATH next to apt libs), the deploy platform's nixpacks version (`libasound2t64` exists only on the 24.04 base; on an older 22.04 base it is `libasound2`).
- 2026-10-17: After deploy, check: (1) build log shows the apt step with the list and `npm ci` without a Puppeteer download error; (2) in the container `ls /app/.cache/puppeteer` lists `chrome` and `chrome-headless-shell`, and `echo $PUPPETEER_CACHE_DIR` prints `/app/.cache/puppeteer`; (3) `fc-list | grep -i -e dejavu -e noto` lists both; (4) on `/admin/reports/<id>` "Download PDF" saves a multi-page A4 PDF with the oat page colour and the running footer; on failure the backend log has Puppeteer's launch error (a missing `lib*.so` names the apt package to add; `PUBLIC_APP_URL` must be reachable from inside the container, since Chrome loads `/print/report` from it). Then tick the acceptance box.
