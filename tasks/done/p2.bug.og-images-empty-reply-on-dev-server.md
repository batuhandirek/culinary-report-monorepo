# Share images answer an empty reply on the running dev server

## Goal
`curl http://localhost:5011/blog/<id>/og.png` and the city pages' `[card=card].png` answer a PNG on the dev server, as they do when the same `GET` runs through Vite's SSR loader.

## Why
On 2026-10-22 every satori image on `:5011` closed the connection without a response ("Empty reply from server", in 0.04 s): the blog's published article's `og.png`, `/berlin/trends/2026-q3/og.png`, `square.png` and `portrait.png`. The same handlers rendered fine (200, image/png) through `vite.createServer().ssrLoadModule(...)` with a stubbed fetch. So cards can't be checked in the running app, and a regression in production would look the same.

## Scope
- In: find why the dev server's `ImageResponse` (`@ethercorps/sveltekit-og`) drops the response (wasm or font loading in the dev process, a stream error swallowed); fix it, or say it is dev-only and confirm a production build (`npm run build`, node adapter) serves the images.
- Out: the cards' design.

## Pointers
- `apps/frontend/src/routes/(blog)/blog/[articleId]/og.png/+server.ts`, `apps/frontend/src/routes/(highlights)/[city=city]/[month=month]/[card=card].png/+server.ts`, `.../trends/[quarter=quarter]/[card=card].png/+server.ts`, `apps/frontend/src/lib/og-image.ts`
- `apps/frontend/.turbo/turbo-dev.log` was empty: the dev server's output is elsewhere

## Acceptance
- [x] A published blog article's `og.png` answers 200 image/png on the running dev server (or on a production build, with the reason dev differs written in `seo-and-ssr`).

## Log
- 2026-10-22: picked up. Reproducing on the running dev server (:5011) and reading the dev stack's output to find why the satori routes drop the connection; assuming the fix belongs in the frontend (config or the routes), not in how the dev stack is started.
- 2026-10-22: root cause found. `ImageResponse` renders in the body stream with `debug: false`, so the failure was silent. With debug on, resvg init threw "Already initialized. The `initWasm()` function can be used only once". `@ethercorps/sveltekit-og` is inlined into Vite's SSR module runner (its `svelte` export condition), while `@resvg/resvg-wasm` is loaded natively by Node. A full SSR reload (`runner.evaluatedModules.clear()`, triggered by editing any loaded module) re-runs the wrapper's resvg loader against the still-initialised native module, so every PNG card fails until the process restarts. Satori (SVG) is unaffected. Reproduced in a throwaway copy on :5099: 200, then an empty reply after touching `lib/og-image.ts`.
- 2026-10-22: fix is `ssr.external: ['@ethercorps/sveltekit-og']` in `apps/frontend/vite.config.ts`. In the copy, the blog og.png and the trends og/square/portrait cards (unpublished berlin 2026-q3 served through a stubbed handleFetch) answered 200 image/png across repeated full reloads, and on a production build (`vite build` + `node build`, where the package is now an external import). Rule added to `seo-and-ssr`. The live :5011 needs a frontend process restart to pick the fix up (a Vite config restart reuses the process, which already has resvg initialised); the coordinator restarts the stack once the backend agents finish.
- 2026-10-22: verified on the live :5011 after the coordinator restarted the stack. Blog og.png for both published articles: 200 image/png. The food trends card in og/square/portrait (rendered by a temporary route of the same `ImageResponse` call with the berlin 2026-q3 fixture, since no month or quarter is published in the dev DB): 200 image/png. Each held through three SSR full reloads forced by editing that temporary route, which was then deleted. Live highlight and trends card URLs answer a clean 404 (nothing published), not an empty reply. `npx svelte-check --threshold error`: 0 errors. No backend change, so no backend tests or journeys were needed. Shipped: `apps/frontend/vite.config.ts` `ssr.external` and the `seo-and-ssr` rule.
