# Make one topic tree

**Read first**: the brief `statements-and-concepts` (the ELI5 table, Analysis §1, decisions 1 and 2), then this.
Program order: **topics-tree** → `terms` → `statements` → `reread-sources-with-new-agents` →
`google-tags-as-statements` → `talked-about-pages`.

## Goal
`Topic` (table `topics`) holds every kind of thing people talk about: today's food topics and, as rows of kind
`aspect`, the nine feedback topics as roots and the ~51 themes as their children (keys kept, the nine `_other`
catch-alls folded into the roots). The theme vocabulary in code is gone; the agents read the legend from the
table and answer a key the code checks; every reader takes labels and roots from the table; an admin edits an
aspect in the topic dialog. No behaviour or count changes otherwise. No LLM spend.

## Why
Two vocabularies (food topics in a table, themes in code) are why "who talked about X" can't be asked across
both and why the term table of the next phase would need a kind discriminator on every link. The user (2026-10-29):
one table, "Topic" for all, rename now so the word means one thing everywhere and nothing is touched twice.

## Scope
- In: the rename (one mechanical commit), kind `aspect` + `hint`, the seed and data migrations, the agents off the
  enum, every reader off `FEEDBACK_THEMES`, labels through the API, the admin topic dialog and list for aspects,
  tests, the skill.
- Out: terms (`terms`), statements (`statements`), any change to what is extracted or counted, the Terms tab,
  merging the theme page into the topic page (`talked-about-pages`), re-reading sources.

## Entity changes (this phase only)
- `FoodTopic` → `Topic`; `FoodTopicKindEnum` → `TopicKindEnum` + `ASPECT`; new column `hint` (text, nullable).
- `MentionFoodTopic` → `MentionTopic`, `MenuItemFoodTopic` → `MenuItemTopic`, `VenueFoodTopic` → `VenueTopic`,
  `FoodTopicIgnoredWord` → `TopicIgnoredWord`; properties `foodTopic(s)` → `topic(s)` on `Mention`, `Hashtag`,
  `FeedbackPoint`, `DishName`.
- `FeedbackPoint.theme` stays the text key (what the SQL readers filter on) and gains the relation `aspect` → `Topic`
  by id (column `aspect_id`, `set null`), set together by every writer; `FeedbackPoint.topic` (the root key) stays,
  derived by `realign`, until `statements` drops it. (Chosen over the FK-by-key the plan assumed: a reference by
  the primary key needs no loaded entity to write, and the key column keeps every reader's SQL unchanged.)
- Deleted: `venues/constants/feedback-themes.constant.ts`, `FeedbackTheme` / `FeedbackTopic` types,
  `FEEDBACK_THEME_LABELS` and the feedback part of `TOPIC_LABELS` (frontend).
