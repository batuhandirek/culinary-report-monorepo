# Read each review and post with one gpt-5.4 call

## Goal
Production reads a review or a post with **one call on gpt-5.4** (`full` tier) that writes the claims *and* each
claim's parts (sentiment, aspect, kind, foods, amount) together, instead of agent A on mini and then agent B on mini
once per claim. The eval shows it no worse than today's A + B on any metric and better on the post metrics. A and B
stay in the code: B for refilling parts without re-reading, A + B as the setup the eval checks when the user wants to
move back to mini later.

## Why
- **Quality.** The gpt-5.4 "second reader" (`apps/backend/eval/runs/second-gpt54`, the eval's reference task run on
  gpt-5.4: one call, A's and B's rules, claims and parts together) is in effect this design. On the held-back cases,
  against today's `one-v2` (A + B on mini): post claims that are real 85 → 96, post aspect 67 → 79, post sentiment
  89 → 96, places that are places 85 → 94, brand match 90 → 97, foods precision posts 72 → 86 and reviews 76 → 91,
  review sentiment 93 → 99. It ran with the reference agents' input, not production's, so it is a hint, not a result.
- **Tokens.** B runs once per claim and carries most of the cost. Measured: today ~26k tokens a review and ~58k a post
  (`runs/one-v2/results`); the one-call gpt-5.4 reader ~3.9k a review and ~9.6k a post (`runs/second-gpt54/results`).
  Dev Berlin brings ~210 reviews and ~125 posts a day (October), so ~13M tokens a day today vs ~2M a day, which is
  the gpt-5.4 free allowance of the two OpenAI accounts (1M a day each). It fits, with no room to spare.
- **The user's rules:** production never pays (only OpenAI's free allowance; `llmPaid` is for hand-started eval work,
  backend `CLAUDE.md`); one item per call (one source a call, never several sources packed with ids); every wording
  and claim kept as said.

## Scope
- In:
  - A one-call reader per source kind (review, post), a new agent each, on `full`. Its rules are composed from the
    existing agents' rules (`ReviewClaimsAgent` / `PostClaimsAgent` + `ClaimPartsAgent`, through `rulesFor`), never
    copied text, so A's and B's rules stay the single source. `PostReferenceAgent` and `ReviewReferenceAgent` already
    compose them this way (`specA`, `specB`, `stepBlock`, `REFERENCE_PREAMBLE`): start from there. Coaching: start
    from A's and B's coaching combined, then tune on the train side.
  - The fixed instructions hold nothing that differs per source (city, own brand, place go in the message), and pass
    1,024 tokens so OpenAI caches them (backend `CLAUDE.md`, "One item per call").
  - Production uses it: `ReviewService.analyse` and `MentionExtractionService` (`extract` and `reread`). Each claim's
    parts are read from its answer through `claimPartsOf`, quotes through `verbatimQuote`; B is not called for those
    claims and they are not left pending for the `statement-parts` backlog. Long posts keep `postClaimsPlan`'s split
    and `mergePostParts`. Places, matching (`VenueMatchAgent`, `decideMatch`) and the gate stay as they are.
  - The eval runs it through the same shared input and answer functions (ingestion-eval rule "the eval sends the
    agents what production sends"), with a switch on `run` to pick the reader (one-call or split A + B) and its model.
  - The reader runs on `openai/gpt-5.4` only (free). Build the model switch on `run` so another model can be tried
    later without code changes.
- Out:
  - **Several sources in one call** (`pipeline.md`'s "batch 5 reviews"): packed calls drop items; measured.
  - **Matching venues before reading and handing the reader candidates** (`pipeline.md`'s "pre-matcher"): in
    round 5 (`eval/climbs/pipeline/log.md`), showing agent A account info made it list venues the text never named
    and places precision fell. A separate experiment if wanted later.
  - `pipeline.md`'s other points are already true: B sees the quote, the place and 15 neighbouring claims
    (`claim-parts-input.ts`); claims must name what they are about, never "it" (`review-claims.agent.ts`
    `claimSchema`); A sees the tagged location and mentioned accounts (`post-claims-input.ts`); wordings are
    looked up by `termKey` and only new ones go to agent C; topics are a tree. Its aspect names (`price_value`,
    `wait_time`) are not ours.
  - Agent C, matching, the aspect table.
  - Re-reading the stored sources with the new reader (`reread-sources-with-new-agents`): asked for separately, see
    Open questions.
  - The Opus judge pass on `one-v2` (~$16): the user said hold.
  - **A Claude reader, deferred by the user (2026-11-03, "not for now").** The user would take one in production if
    it gains a lot over the free reader and fits the ~$100 credit comfortably. Estimates for when it comes back,
    from the reference costs (a review $0.06–0.12, a post $0.14–0.31 on Opus): Opus ~$30–60 a day (does not fit),
    Sonnet ~$15–30 a day (does not fit), Haiku ~$0.75–1.5 a day (~$25–45 a month before caching; an eval run on
    all cases about $1). An Opus reader is partly graded by itself (the answer key is Opus's). No paid run in this
    task.

## Acceptance
- [ ] A one-call reader for reviews and one for posts, on `full`, one source a call; rules composed from A's and B's
      `rulesFor`; fixed instructions over 1,024 tokens with every per-source detail in the message.
- [ ] `ReviewService.analyse` and `MentionExtractionService.extract` / `reread` use it; each claim's parts come from its
      answer through `claimPartsOf`; B is not called for them; long posts still split and merge as today.
- [ ] A source whose call fails because the allowance is out stays unread and is read on a later day; nothing moves
      to Claude, and nothing is stored as read with no claims.
- [ ] PGlite tests (reader stubbed): a review and a post are written with claims and parts in one call and B is never
      called; a fatal provider error leaves the source pending.
- [ ] Eval: `run` takes the reader switch; the one-call reader run twice on all cases, compared with `one-v2`
      (noise `mini-v6,mini-v6b`) and logged in `apps/backend/eval/climbs/one-call-reader/log.md` with the tokens per
      review and per post measured. A run of 371 cases is ~2.6M tokens, more than one day's gpt-5.4 allowance:
      results on disk are kept, so a run resumes the next day.
- [ ] Shipped only if no metric is worse beyond noise and the post metrics are better; otherwise logged, and the split
      A + B stays in production.
- [ ] The pipeline's gpt-5.4 tokens over one dev day measured and logged against the 2M allowance.
- [ ] Skills fixed in the same change: `domain-venues-and-reports` (the agents, the roster's tiers, B's role),
      `ingestion-eval` (the reader switch, what is judged on which model); backend `CLAUDE.md` if a rule moved.
