# One Google Maps "places" atom for every place search and detail scrape

## Goal

Every Google Maps call in the app goes through **one atom**, `places`. The atom is a typed actor call (`GOOGLE_PLACES_ACTOR` in `apify/actors/google-places.actor.ts`) run as a child workflow on the `apify` queue, so it gets the credit wait and is one of 4 runs at a time. Its items are saved through **one** path in `VenueScrapeService`.

Each business rule that uses it keeps only its own two parts:
- **its plan**: which queries or place ids, how many results, what cap;
- **its reading of the results**: lookups' bookkeeping, a brand's branches, a dish's ranks, a venue's live busyness.

The six hand-built actor inputs and the three save loops go away.

This is the first slice of the **atoms** direction: scrapes are a few kinds of provider call (atoms), plans live in the domain services, and the pipeline's operations are rules composing them (`operations.md`, section 6). Reviews and profiles follow the same shape in their own tasks (see "Next atoms").

## Why

**Today: one actor, six call sites, three save paths** (2026-11-06, `apps/backend/src/modules/venues/services/venue-scrape.service.ts`):

| Caller (operation) | Method | Input built by hand | Save |
|---|---|---|---|
| `scrape-venues` | `scrapeCity` | `searchStringsArray` terms + `locationQuery`, `maxCrawledPlacesPerSearch` 1000 | `saveAll` (source CITY, openings after the first), stamps `City.venuesScrapedAt`, `fillDistricts` |
| `lookup-venues` | `lookupNames` | names + `locationQuery`, 3 each | `saveFound` + `VenueLookup` rows (names looked up within `LOOKUP_RETRY_MONTHS` skipped) |
| `scrape-venues` (SEARCH_BRANCHES), the brand page's "Find branches" (`BrandSearchJob`) | `searchBrands` via `BrandService.searchCity` / `searchBranches` | brand names + `locationQuery`, 40 each | **a loop of its own** over `saveGooglePlace`, branch picking (`isBrandName`), `fillDistricts`, `queueAutoMerge` |
| `osm-places` (`OsmPlaceService.lookup`), `ProfilePlaceService.searchAddresses` | `searchPlaces` | queries as typed, no `locationQuery`, `perSearch` | `saveFound` |
| `read-mentioned-profiles` | `placesSearchInput` + `apifyService.runActor` from the workflow | the same as `searchPlaces` | `ProfilePlaceService.saveAddressSearch` → `saveFound` |
| `dish-searches` (`DishSearchService.sweep`) | `searchEach` | one run per query from `citySearchUrl` (a map centred on the city), `runPool` of 4 **inside the step** | `saveFound`; ranks read from the items |
| `refresh-venue-details`, `sample-busyness` (`VenueBusynessService.sample`) | `refreshDetails` → `scrapeDetailPages` | `placeIds` + `scrapePlaceDetailPage`, `scrapeOrderOnline` | `saveAll` (source DETAILS, known venues only) |

What's wrong with it:
- **Untyped.** Every input is an untyped object literal repeating `language`, `maxReviews: 0`, `maxImages: 0` and `maxQuestions` (sometimes forgotten), and every item is cast to `GooglePlaceItem`.
- **Off the `apify` queue.** The runs happen inline inside a pipeline step, so they skip the `apify` queue's concurrency (4) and the credit wait. `searchEach` even runs 4 at once with `runPool` inside one step. With all the month operations starting together on the 2nd, the Free plan's 5 concurrent jobs can be exceeded (`operations.md` §6).
- **Three ways to save the same item.** `saveAll`, `saveFound` and `searchBrands`' own loop differ only by source and by whether new places may join the city.
- **Domain services run scrapes themselves.** `DishSearchService.sweep`, `OsmPlaceService.lookup`, `BrandService.searchCity`, `VenueBusynessService.sample` and `ProfilePlaceService.searchAddresses` each plan, call and save in one method. A workflow therefore can't make the call a child, and the pipeline step is one opaque blob.

## Scope

### In: the atom

1. **The actor file `apify/actors/google-places.actor.ts`**: **done (2026-11-06)**. `GOOGLE_PLACES_ACTOR`, `GooglePlacesInput`, `GooglePlaceItem` exist (`venue.service.ts` re-exports the item, `SearchPlaceItem` is an alias of it). Left: `VenueScrapeService`'s own string `GOOGLE_PLACES_ACTOR` (also imported by `read-mentioned-profiles`), which this task deletes. What the file holds:
   - `GooglePlacesInput`: the union of what we send, typed.
   - `GooglePlaceItem`: moved from `venues/services/venue.service.ts`; venues re-exports it until its callers move.
   - The actor's quirks in its doc comment:
     - $0.004 a place (`GOOGLE_PLACE_USD`);
     - a run's cap must reach $0.50;
     - each place is output once per run (why the dish searches run one search per run);
     - without a location the map sits where the proxy is (New York, Dallas).

2. **The input builders**: one pure function per mode, in `venues/util/places-input.ts`, so the four modes are named and the shared flags written once:
   ```ts
   // venues/util/places-input.ts
   const LIST_ONLY = { language: 'en', maxReviews: 0, maxImages: 0, maxQuestions: 0 } as const;

   /** Text searches on the city's map grid (`City.locationQuery`): the venue list, lookups, brand names */
   export const gridSearch = (city: Pick<City, 'locationQuery'>, queries: string[], perQuery: number): GooglePlacesInput =>
   	({ ...LIST_ONLY, searchStringsArray: queries, locationQuery: city.locationQuery, maxCrawledPlacesPerSearch: perQuery });

   /** Searches typed as a guest types them, the city in the text, Google's own order: OSM places, profile addresses */
   export const typedSearch = (queries: string[], perQuery: number): GooglePlacesInput =>
   	({ ...LIST_ONLY, searchStringsArray: queries, maxCrawledPlacesPerSearch: perQuery });

   /** One search from a map centred on the city: a run of its own, so its order is whole (dish searches) */
   export const mapSearch = (city: Pick<City, 'lat' | 'lng'>, query: string, perQuery: number): GooglePlacesInput => {
   	const url = citySearchUrl(query, city);
   	return { ...LIST_ONLY, ...(url ? { startUrls: [{ url }] } : { searchStringsArray: [query] }), maxCrawledPlacesPerSearch: perQuery };
   };

   /** Detail pages of known places: popular times, every amenity, the "Order online" links */
   export const detailPages = (placeIds: string[]): GooglePlacesInput =>
   	({ ...LIST_ONLY, placeIds, scrapePlaceDetailPage: true, scrapeOrderOnline: true });
   ```

3. **One save path.** `VenueScrapeService.savePlaces(items, { city?, source, newPlaces })` replaces `saveAll`, `saveFound` and `searchBrands`' loop:
   - `newPlaces: 'none'` (details: known venues only);
   - `newPlaces: 'food-in-city'` (searches: known venues updated, a new food place in the city added);
   - `newPlaces: 'all'` (the city's own list).
   - It flushes in chunks, fills districts and queues the auto-merge once per call. `scrapeCity`'s `venuesScrapedAt` stamp and openings flag become arguments.
   - It returns `{ saved, venueIds: Map<placeId, venueId> }`, so a caller can read the venues back without matching names again (the branch picking needs this).

4. **The atom workflow**: `pipeline/atoms/places/` (the first folder of `pipeline/atoms/`):
   ```ts
   // pipeline/atoms/places/workflows/places.workflow.ts
   export interface PlacesRun {
   	cityId: string | null;          // null: detail pages of known places, any city
   	input: GooglePlacesInput;       // from the builders above, plain JSON
   	maxCostUsd: number;
   	purpose: string;                // the ApifyRun's purpose: "google-places lookups Berlin: 412"
   	save: { source: VenueScrapeSourceEnum; newPlaces: 'none' | 'food-in-city' | 'all' };
   	memoryMbytes?: number;
   }

   /** What a caller reads back: never the items (they stay on the ApifyRun row), only what it needs */
   export interface PlacesResult {
   	recordId: string;               // ApifyRun.id: `ApifyService.storedItems(recordId)` reads the items again
   	found: number;
   	saved: number;
   	/** Per query (the item's `searchString`, or the start URL's), the place ids in Google's order */
   	byQuery: Record<string, string[]>;
   	/** Place id → our venue id, for the places we keep */
   	venueIds: Record<string, string>;
   }

   @Injectable()
   export class PlacesWorkflow {
   	@DurableWorkflow({ name: 'places.run' })
   	@EnsureRequestContext()
   	async run(run: PlacesRun): Promise<PlacesResult> {
   		const items = await runActorCall(this.apifyService, {
   			actor: GOOGLE_PLACES_ACTOR, input: run.input, maxCostUsd: run.maxCostUsd, purpose: run.purpose,
   		}, { memoryMbytes: run.memoryMbytes });   // a child on the `apify` queue: credit wait, 4 at a time
   		return this.save(run, items);           // one step
   	}

   	@DurableStep({ name: 'save places' })
   	private async save(run: PlacesRun, items: GooglePlaceItem[]): Promise<PlacesResult> { … VenueScrapeService.savePlaces … }
   }
   ```
   - **Idempotent by its input.** `ApifyService.runActor` already dedupes a run by actor plus input hash, so two rules asking for the same search while one runs share it.
   - **Called from a rule's body** as `this.places.run({...})`, a child workflow. Several are fanned out by starting each (`durable.start`) and then awaiting them in order, as `readCity` does.
   - **The item is never returned.** `byQuery` and `venueIds` are what callers read: ids, a few thousand at most. A caller that needs more fields (busyness' live percent, a dish's rating at its rank) reads them from the stored items by `recordId` in its own save step. The rule: never let a step or workflow return bulk data.

### In: the callers become plan → atom → read

Each domain method that ran a scrape is split. The plan and the reading stay in the domain service; the call moves to the operation's body.

- **`lookup-venues`** (before: `LOOKUP_VENUES` step = `venueScrapeService.lookupNames(city, names, budget)`):
  ```ts
  const plan = await this.planLookups(cityId);            // step: VenueScrapeService.planLookups(city, unmatchedNames, budget)
  //   → { queries: string[]; perQuery: 3; maxCostUsd } (the names not searched within LOOKUP_RETRY_MONTHS)
  if (plan.queries.length) {
  	const found = await this.places.run({ cityId, input: gridSearch(city, plan.queries, 3), … , save: { source: LOOKUP, newPlaces: 'food-in-city' } });
  	await this.recordLookups(cityId, plan.queries);      // step: VenueScrapeService.recordLookups (the VenueLookup rows)
  }
  ```
  (`city` here is the plain `{ locationQuery }` the plan step returns, never the entity.)
- **`scrape-venues`**:
  - The city list: `due` → `places.run(gridSearch(city, ['restaurant','bar','cafe'], 1000), save: { source: CITY, newPlaces: 'all', openings: city scraped before })` → step `VenueScrapeService.markCityScraped` (the stamp, then `fillDistricts`).
  - Then SEARCH_BRANCHES: `BrandService.planBranchSearch(city)` (the chains' names) → `places.run(gridSearch(city, names, 40))` → step `BrandService.saveBranchSearch(city, result)`, which picks branches from `byQuery` + `venueIds` with `isBrandName` and auto-merges.
  - The brand page's "Find branches" job (`BrandSearchJob` / `BrandSearchWorker`, pg-boss) becomes a small workflow of its own (`pipeline/brand-branch-search/`, or the atom started from the controller): plan → `places.run` → save.
- **`osm-places`**:
  - Before: `LOOKUP_OSM_PLACES` = `OsmPlaceService.lookup(city, budget)`, which plans, calls `searchPlaces` and matches.
  - After: step `OsmPlaceService.planLookups(city, budget)` → `{ osmPlaceIds, queries }`, then `places.run(typedSearch(queries, 1))`, then step `OsmPlaceService.saveLookups(city, osmPlaceIds, result)`, which stamps `lookedUpAt` and matches again.
- **`read-mentioned-profiles`**: drop its hand-written `apifyService.runActor(GOOGLE_PLACES_ACTOR, venueScrapeService.placesSearchInput(...))` for `places.run(typedSearch(...))`. `ProfilePlaceService.saveAddressSearch` reads `venueIds` instead of the raw items.
- **`dish-searches`**: the biggest win.
  - Before: `TRACK_DISH_SEARCHES` = `DishSearchService.sweep(city, budget)` = plan, `searchEach` (`runPool` of 4 inside the step) and save the ranks.
  - After:
    ```ts
    const plan = await this.planSweep(cityId);               // step: DishSearchService.planSweep(city, budget, now)
    //   → { searchedOn, searches: { query, topicKey, district }[], perQuery: 10, notSearched }
    const handles = [];
    for (const s of plan.searches)                           // every search its own run: its order is whole
    	handles.push(await this.durable.start(this.places.run, [{ cityId, input: mapSearch(city, s.query, 10), maxCostUsd: 0.5, … }]));
    const results = [];
    for (const h of handles) results.push(await h.getResult().catch(e => ({ failed: e.message })));
    return this.saveSweep(cityId, plan, results);            // step: DishSearchService.saveSweep: the ranks from byQuery + venueIds
    ```
  - The 4-at-a-time limit is now the `apify` queue's, shared with every other run, instead of a `runPool` that knows nothing of them.
- **`refresh-venue-details`**: `places.run({ cityId: null, input: detailPages(placeIds), save: { source: DETAILS, newPlaces: 'none' } })`. The `withPopularTimes` count is read in the save step from the stored items.
- **`sample-busyness`**:
  - Step `VenueBusynessService.planSample` → the place ids.
  - Then `places.run(detailPages(ids))`.
  - Then step `VenueBusynessService.saveSample(recordId)`: the histograms and live percent from the stored items (`ApifyService.storedItems`).

### In: what goes

- From `VenueScrapeService`: `scrapeCity`, `lookupNames`, `searchBrands`, `searchPlaces`, `placesSearchInput`, `searchEach`, `scrapeDetailPages`, `refreshDetails`, `saveAll` and `saveFound`. In their place: `savePlaces`, `planLookups` / `recordLookups` and `markCityScraped`.
- `DishSearchService.sweep`, `OsmPlaceService.lookup`, `BrandService.searchCity` / `searchBranches`, `VenueBusynessService.sample`, `ProfilePlaceService.searchAddresses`: each split into a plan and a save.
- `SEARCH_RUNS_AT_ONCE`, `SEARCH_RUN_MEMORY_MB` (the memory moves to the dish search's `PlacesRun.memoryMbytes`).
- The `GOOGLE_PLACES_ACTOR` string constant in `venue-scrape.service.ts`. The typed actor is the one name.

### Out

- The reviews actor (`compass/Google-Maps-Reviews-Scraper`, a different actor). It gets the next atom task, as do the profiles.
- Changing what any search asks for or how many results it keeps: the inputs stay what each caller sends today, with one deliberate exception. `maxQuestions: 0` is added to the three grid searches (`scrapeCity`, `lookupNames`, `searchBrands`), which leave it out today. Q&A carries personal data and is out of scope (the skill's details rule), and nothing reads it.
- The OSM sync (Overpass, a plain fetch, no actor).
