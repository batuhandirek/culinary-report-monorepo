# Move the remaining kind-of-food readers from normalizeCuisine onto food topics

## Goal
Search-rank queries, openings and closures by food, the trends page's cuisine table and the report's city section group by food topics (`FoodTopicIndex`, `VenueFoodTopicService.tags`) instead of raw `normalizeCuisine` keys, so a compound ("Vegan Döner") and an alias ("Iranian" → Persian) count as the topic, and an admin's venue tags apply there too.

## Why
Each reader has its own rule today; topics are the one taxonomy the admin now edits. Without this, mapping a word on `/admin/topics` changes trends searches and competitors but not these four.

## Scope
- In: `venues/util/search-ranks.ts` (queries from the venue's primary and other food tags × district; drop `GENERIC_CATEGORY_KEYS` once nothing uses it), `venue-status-change.service.ts` (`quarter` by the venue's primary topic label), `trends/util/compute-trends.ts` (cuisine shares by a mention's first topic, so tables still sum to 100), `reports/util/city-section.ts` (the venue's kind of food = its primary topic; rising rows by topic).
- Out: the search-interest panel (already on topics), competitor suggestions (done).

## Pointers
- `rg normalizeCuisine apps/backend/src`
- `food-topics/util/venue-topics.ts`, `food-topics/services/venue-food-topic.service.ts`

## Acceptance
- [x] PGlite: each reader groups by topics; the trends tables still sum to 100; `ReportData` shape unchanged (the city section's `cuisine.key` is now a topic key). (`venue-search-rank`, `venue-status-change`, `trend.service`, `city-section`, `report-city` suites)

None.
