# Move the remaining crons and agent loops onto durable workflows

## Goal
Every cron in `dbos/operations.md` is a `@DurableSchedule` and every agent call in it goes through `DurableLlmService.generate`, which always waits until an account can serve (there are no quota modes: the user, 2026-11-06). Where an operation must not wait (the 22:00 backlogs burn only what the day leaves; the review-watch's alert goes out without a draft) the workflow decides it, at the workflow level. `ReportAnalysisAgent`'s bounded tool loop runs as a workflow with each LLM turn and each evidence tool call a step.

## Why
Done so far: the hourly reading (`pipeline-ingest-hourly`), the daily backlog drain (`llm-backlog`), the Apify credit snapshot, and the weekly `READ_MENTIONED_PROFILES` as `ReadMentionedProfilesSchedule` (the worked example in the `durable-workflows` skill: one `.schedule.ts` per operation, plan → child → save for every actor and agent call). The rest (`landing-editions` 06:30, `weekly-listening` Sun 03:00 with `ProfilePlaceAgent`, `review-watch` Mon 05:00, `monthly-pipeline` 2nd 06:00 with `BUILD_REPORTS`' three agents, the daily Instagram/creator/post-count/follower crons) still run as pg-boss crons calling plain services: a model out fails or stalls them with no visible run.

## Scope
- In: each `pipeline/crons/*.cron.ts` and `landing`'s cron as a `schedules/*.schedule.ts` (the cron queues pipeline runs, so the first slice is the schedule itself; the runs become workflows in `pipeline-runs-as-workflows`); `LandingCopyAgent`, `ProfilePlaceAgent`, `ReviewReplyAgent`, `ReportAnalysisAgent`, `ReportEditorAgent` calls through `DurableLlmService.generate`; the report agent's tool loop as `ReportWorkflows.analyse(brandId, month)`.
- In: the 22:00 drain keeps ending a backlog for the day when its batch finds no model (today the batch throws and the drain records `allowance`); it checks `availability` itself rather than waiting in the gateway.
- In (the user, 2026-11-06): **each operation in a folder of its own** under its module (`modules/pipeline/<operation>/`: workflow, schedule, queue, constants, DTOs, services, controller), as `read-mentioned-profiles/` and `creator-watch/` are, the step's code moved out of `PipelineService` (which goes once the last step has).
- In (the user, 2026-11-06): **every actor an `apify/actors/*.actor.ts`** (`defineActor<Input, Item>(id)`: the typed input and item, its price, minimum cap and Free-plan quirks; no domain logic), run with `runActorCall(apify, { actor, input, maxCostUsd, purpose })`; the service that used it keeps the mapping of its items to our domain and offers the per-step pieces a workflow needs (the `ActorCall` as plain data, the save as a method), as `AccountScrapeService` does for the two profile actors. Done: `instagram-profile`, `tiktok-profile`. Left (17): the TikTok search, hashtag, comments and scraper actors, the Instagram scraper and location actors, Google Places, Google Maps reviews, Google search and news, TripAdvisor reviews, Google Trends (signalbench, steadyfetch), Wolt, Lieferando, TheFork, OpenTable: each moves when its step becomes a workflow. Once every caller runs actors from a workflow's body, `runActor`'s inline path (inside a step or from plain code) goes, and an actor run always is a child workflow.
- Out: pg-boss events (notifications, e-mails) stay on pg-boss.
