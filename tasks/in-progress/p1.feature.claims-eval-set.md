# Ingestion eval

## Goal
Every change to agent A (`ReviewClaimsAgent`, `PostClaimsAgent`), agent B (`ClaimPartsAgent`), agent C
(`TermTopicAgent`) or matching (`VenueMatchAgent` and the code around it) gets a score on the same cases, field by
field, against reference answers Opus wrote, and the data already stored gets the same score, so we know whether it is
worth paying to re-read it.

## Why
A read on 2026-10-31 (12 random reviews, 6 random posts) found about a quarter of the claims with a problem, posts
worse than reviews: pronoun claims that lose their dish ("both were incredibly delicious"), fragments that are no
claim ("with friends"), `other` as a dumping ground, wrong aspects ("best kebab in Berlin" → `location`, "worth the
wait" → `value_for_money`), post claims about the place filed as `none`. Each earlier fix was judged on a handful of
samples.

## Design (agreed with the user, 2026-11-01)
- **Cases** (`apps/backend/eval/cases/{reviews,posts,terms}/<id>.json`, one file a case, in git): ~150 reviews and
  ~150 posts and articles of dev Berlin, stratified (platforms, languages, stars, length, chains, own posts,
  multi-place articles, transcripts or not), ~500 food wordings (an admin's decision is its own reference). Each case
  copies the source exactly as the agents see it (the same input builders the services use) and what is stored now
  (claims with their parts, mentions with their match, a term's links), so the set is independent of the dev DB.
- **References by Opus 5.5** (`npm run eval -- reference`): one call per review or post with the pipeline agents'
  own instructions as the spec (A and B together; for posts the places too), then one matching call per reference
  place over candidates read from the dev DB (a wider net than the matcher's five). A term batch gets C's spec. Each
  claim may be `optional` and carry `alsoAcceptable` aspects, sentiments and kinds, so taste is not scored as error.
  An answer from any model but Opus is discarded (the roster puts gpt-5.4 behind it). The spec's hash is kept so a
  report says when references predate a prompt change.
- **Runs** (`npm run eval -- run --label <name>`): the current agents on every case (agent A, then B over its claims
  grouped as `StatementPartsService` groups them, matching through `decideMatch` against the dev DB's venues, C on
  the wordings), written to `apps/backend/eval/runs/<label>/`. The stored data is scored as the run `stored`.
- **Scoring**: claims paired one-to-one by meaning (`ClaimPairingAgent`, mini: pairing is no quality judgement),
  then per field in code: claim recall and precision (optional references never missed), subject and place,
  sentiment, aspect (exact and at root), foods (F1 on `termKey`), amount, kind and change precision/recall; places
  recall and precision (paired by name), match accuracy end to end and on the reference places alone; terms topic F1,
  exact sets, first topic, relation, none.
- **Adjudication** (`npm run eval -- adjudicate --label <name>`, opt-in, Opus): every disagreement of a run is ruled
  agent wrong / reference wrong / both fine; the report counts only agent errors, and `--apply` folds the reference
  fixes into the case files.
- **Report**: `apps/backend/eval/runs/<label>/report.md`: totals beside earlier runs, then every miss with its case.
- **Judges are Mastra agents** (the user, 2026-11-01: no Anthropic SDK): Opus is picked per call
  (`generate(…, { model: 'anthropic/claude-opus-5-5' })`), so there is no Batch API discount.
- **Cost** (Opus $4/$20 per M, no batch): references for ~300 sources ~$35–60, terms ~$3, an adjudication ~$3–5;
  runs are on the free mini allowance. The pilot of 5 cases measures it before the full set is paid for.

## Scope
- In: the set, the references, the runner, the scorer, the report, the adjudication, the baseline, the skill.
- Out: changing any prompt (`claims-extraction-fixes`), the gate (left out: the set's posts are ones it digests),
  comments and press, topic discovery (agent D).
