# Link the wordings the code can't place to menu items, and let an admin correct a link

## Goal
A wording a brand's reviews or posts use for one of its menu items is linked to that item even when the name match is not sure ("bulgogi burger" at a place whose menu has "Bussin' Bulgogi" and "Bulgogi Mayo", "Thai burger" for "Banging Bangkok"), and an admin can say "this wording is that item" or "is none" on the brand's Menu tab, final.

## Why
`MenuTermService` links in code only (`matchMenuItem`: the same name, a wording holding the item's name, a close spelling) and leaves anything ambiguous unlinked on purpose. At The Bun Society (2026-11-14) that linked 12 of its 65 items to reviews and posts; Google's own tags there say "bulgogi burger" 34 times, which the code can't tell between two items. The unlinked wordings are where an owner's most-named dishes are undercounted.

## Scope
- In: an agent asked one wording at a time with the venue's menu (names, sections, descriptions) and the claim's quote, answering one item or none; only for wordings of two words or more, or naming a word of an item, that the code left unlinked; its answer stored as a `MenuItemTerm` with its own `method`, a "none" remembered so it is asked once (a column or a row saying so; today a link can only say "is").
- In: the cost first. One wording a call with the menu in the message is roughly a thousand tokens; count the unlinked wordings per brand with a menu before choosing the tier, and say the estimate to the user.
- In: an admin's link and "not this item" on the Menu tab's wordings, never rewritten by `relinkVenues`.
- In: Google's "people often mention" tags matched the same way and shown beside an item's sources (they are terms already; today they are not matched to items).
- Out: changing agent C's global decisions: a house name stays "no food" for every other brand.
