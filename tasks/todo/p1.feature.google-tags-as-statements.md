# Google tags as statements

**Read first**: the brief `statements-and-concepts` (scenario 5, decision 7), then this. Needs `statements` done.
Program order: `topics-tree` → `terms` → `statements` → `reread-sources-with-new-agents` →
**google-tags-as-statements** → `talked-about-pages`.

## Goal
Each tag of a venue's `details.reviewsTags` ("waiting time" ×4,098) is a statement of that venue: `sourceKind
google_tag`, `venue` set, `subject place`, `text` the title, `count` Google's count, `saidAt` the details scrape,
`month` null, `sentiment` null (not judged), its wording a term whose links give the statement its parts. Written
on every details save and replaced when the tags change. The brand Overview's "Google reviews often mention" and the
place page's "Reviews often mention" read these statements and link each tag to its topics; the read-only stopgap
(`reviewTagTopics`, `review-tag-topics.ts`) is deleted. "Which brands' Google tags mention X" is one query.

## Why
Google's tags are the broadest "what guests say" signal we hold (1,011 distinct titles on 166 dev venues) and link
to nothing today. The user: no separate table; Google's words never into dish names as they were; a tag is a
statement whose wording maps to topics like any other.

## Scope
- In: the writer, the backfill over stored details, the two admin panels, the query (as a service method and an
  admin route; its page is `talked-about-pages`), tests, deleting the stopgap.
- Out: scraping more detail pages (the monthly `REFRESH_VENUE_DETAILS` already does), any UI beyond the two panels.

## Order of work
1. `StatementService.replaceGoogleTags(venue, tags, scrapedAt)`: diff by title against the venue's `google_tag`
   statements (update `count` and `saidAt` on a kept title, add new, delete gone), each title upserted as a term
   (`TermService.ensure`; a decided term gives parts at once, a pending one after the `terms` backlog through
   `apply`). Called from `VenueService.saveGooglePlace` after `mergeVenueDetails` when `reviewsTags` is present
   (an absent field is unknown, never "no tags": leave the statements).
2. Backfill: a one-off pass over every venue with `details.reviewsTags` (an admin route `POST /admin/statements/google-tags/backfill`
   or the relink job's first run), stamped `detailsAt`.
3. `BrandSummaryService.reviewTags` and `GET /admin/venues/:id` `reviewTagTopics` read the statements (title, count,
   topics from parts); `reviewTagTopic` / `review-tag-topics.ts` / its spec and the `DishNameService.reviewTagTopics`
   leftovers deleted; the frontend panels link each tag to each topic's page.
4. `StatementService.brandsWithGoogleTag(topicKey, cityId)` ("which brands' Google tags mention X", descendants
   included, the tag titles and counts per brand) behind `GET /admin/topics/:key/google-tags?cityId=`.
5. Tests: `google-tag-statements.pglite.spec.ts` (written on save with counts, replaced when titles change, kept when
   the field is absent, parts after a term decision, the brand query across a chain's branches, the panels' routes).
6. Skill: Google tags rule; the stopgap paragraph removed.
