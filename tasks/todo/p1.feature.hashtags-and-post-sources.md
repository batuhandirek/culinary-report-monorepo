# Hashtags and post sources

## Goal
- **`Hashtag`** is a row: one per normalized tag, across platforms.
- **`PostHashtag`** links a post to every tag in its caption.
- **`PostSource`** links a post to every `CitySource` that found it, not only the first.

The city's Sources view then shows, per hashtag or search, the posts and matched posts it found, and how many of those **only it** found. Tags we don't scrape but that keep appearing on matched posts are suggested as new sources from data, not LLM guesses. Tags that name a food topic (#smashburger) or a brand (#burgerbros) are linked to it.

## Why
- **Yield is undercounted today.** `SocialPost.source` holds one string (`#tag`, `search:q`, `place:…`, `blog:…`), and `SocialPostService.upsert` (`social/services/social-post.service.ts` ~line 44) keeps it "as first seen" when another source finds the post again. `CityService` yield (~line 225) groups by that one string. A post found by #berlinfood and #berlineats counts for one of them only.
- **Unique yield is what spending is decided on.** Apify stays on the Free plan, so hashtag pages are capped (memory: `apify-free-plan-only`; costs in `pipeline/constants/pipeline.constant.ts`). The question is "if we drop this hashtag, what do we lose?", which needs every source per post.
- **Hashtags are stored but not usable.** They're a jsonb `string[]` on the post, read only as LLM context (`mention-extraction.service.ts` ~line 252). "Which tags appear on posts about matched venues" needs `jsonb_array_elements` over every post.
- **Source suggestions are guesses.** `CitySourceSuggestionAgent` (`cities/agents/city-source-suggestion.agent.ts`) proposes hashtags from the model's knowledge. Co-occurrence on matched posts is real evidence, and free.

## Design
- **`Hashtag`** (`hashtags`, social module): `tag` (unique, normalized: lowercase, no `#`, Unicode letters kept, so `#BerlinFood` and `#berlinfood` are one), `foodTopic` → `FoodTopic` (nullable, set null), `brand` → `Brand` (nullable, set null), `ignored` (boolean, for noise like #fyp, #foodie, #viral, the way `FoodTopicIgnoredWord` marks cuisine words).
- **`PostHashtag`** (`post_hashtags`): `post` (cascade), `hashtag` (cascade), unique pair. It replaces `SocialPost.hashtags`. The extraction prompt reads the tags through the relation.
- **`PostSource`** (`post_sources`): `post` (cascade), `source` → `CitySource` (cascade), `foundAt`, unique pair. `upsert` adds a row whenever a source finds the post, new or known. It replaces `SocialPost.source`. `place:<venue>` (a venue's own location page) and the blog kind need a check: a blog is a `CitySource` already; a place scrape isn't. Give `PostSource` a nullable `source` plus a `kind` for the non-`CitySource` finds, or a `venue` link for `place:`, whichever the code supports more cleanly.
- **`CitySource` ↔ `Hashtag`**: a hashtag source gets `hashtag` → `Hashtag` (nullable, set for the two hashtag kinds), so "is this tag already scraped in this city" is a join.
- **Food topic and brand links**, pure and no LLM:
  - `foodTopic` by `FoodTopicIndex.exact(tag)`, and by splitting run-together tags against topic keys and aliases only if that turns out precise. Re-linked by `FoodTopicRelinkJob` from `food-topic-links` (register there, or add the job here if this lands first).
  - `brand` when the tag equals a brand's normalized name or one of its own accounts' handles. Re-checked on brand merges.
- **Yield view** (`CityService` yield, the city's Sources tab): per source, posts, matched posts and **unique matched posts** (matched posts no other enabled source found) over the last three months, from `PostSource`.
- **Suggestions from data**: per city and three months, tags with no `CitySource` and not `ignored`, ranked by matched posts they appear on, with distinct brands and a sample. Shown next to the LLM suggestions with an "Add as source" action that creates the disabled-then-enabled `CitySource` the way suggestions work today (`city.service.ts` ~line 153).
- **Backfill**: from stored `hashtags` and `source` on every post: one `PostHashtag` per tag, one `PostSource` for the stored source. Past re-finds are lost, so the unique counts become right going forward. Say so on the view until three months have passed.

## Scope
- In: the three entities, the upsert change, the backfill, the yield view with unique yield, data-driven suggestions, the food topic and brand links, the ignore list, tests, the skill, `ENTITIES.md`.
- Out:
  - Using hashtags as a food signal for venue tags: `food-topic-links` can add them as a source later, if they turn out precise.
  - `taggedHandles` (accounts tagged in a post). It's the same kind of link (post → `SocialAccount`), and worth its own small task if the account matching wants it.
  - Hashtag trends on public pages.
