# Food topic links

## Goal
Every "what kind of food is this" answer is stored as rows that point at `FoodTopic`:
- **A mention's cuisine**: "Vegan Döner" links to vegan and kebab, its parents counted by the readers.
- **A venue's tags**: burger place, döner place, its primary food. Today only admin tags are stored.
- **A menu item's topics.**

One re-link job keeps them current when topics or aliases change. "All burger places in Berlin", "posts about Turkish food in September" and "waiting complaints at burger places" become joins on indexed rows. Together with `opinions-table` (feedback points with `foodTopic`), no reader resolves food text at read time any more.

## Why
- **Mention cuisine is resolved in about six places**, each calling `FoodTopicIndex.resolveMention` on the fly:
  - `trends/util/compute-trends.ts` (`mentionTopic`)
  - `trends/util/topic-mentions.ts` (`countTopicMentions`)
  - `reports/util/city-section.ts`
  - `food-topics/services/venue-food-topic.service.ts` (the mention cuisines feeding venue tags)
  - `trend.service.ts` loading
  - `food-topic.service.ts` `overview` (the unrecognised-words list: that one keeps reading text, see Scope)
- **A venue's tags are recomputed from scratch on every call.** `VenueFoodTopicService.tags` (`food-topics/util/venue-topics.ts`: categories, posts' cuisines, menu items, Google's review tags, admin tags, scored, with a primary) is called from eight places: `report-city.service.ts` (twice), `competitor.service.ts`, `venue-status-change.service.ts`, `venue-search-rank.service.ts`, `theme-insight.service.ts` (`brandFoods`), `topic-insight.service.ts` and `menu-topic.service.ts`. Each loads the inputs again. No query can filter venues by kind of food.
- **Menu items are resolved on read** (`resolveMenuItem` in `food-topics/util/menu-topics.ts`) for prices per kind of food.
- The topic list changes (aliases added, topics moved under a parent). Today that is why matching on read was chosen, and the re-link job keeps that property with stored rows.

## Design
- **`MentionFoodTopic`** (`mention_food_topics`, food-topics module): `mention` (cascade), `topic` (cascade), `source` `cuisine` | `category`. Written for the mention's own cuisine (`index.resolve(mention.cuisine)`). When the cuisine names nothing, the readers fall back to the matched venue's Google category (`resolveMention`). Store that fallback as `category` rows only if the venue is known, and re-derive them when the mention is re-matched (`MentionMatchingService`, `admin-mention-corrections`), so a re-match updates its food. Store topics as resolved, without parents; readers expand parents with `withParents`, as now.
- **Venue tags stored**: `VenueFoodTopic` today holds an admin's tag or exclusion. It gains the computed tags too: `source` (`admin` | `category` | `posts` | `menu` | `review_tags`, the `VenueTopicSource` values), `score`, `primary`, with `excluded` kept for admin rows.
  - `VenueFoodTopicService.refresh(venues)` runs `venueTopics` and replaces the computed rows. Admin rows are never touched by it.
  - `tags()` reads rows instead of computing.
  - Refresh when an input changes: after `EXTRACT_MENTIONS` / matching, `REFRESH_VENUE_DETAILS` (categories, review tags), `SCRAPE_DELIVERY` (menus), for the city's venues, as a step or a job at the end of each; after an admin tag change, for that venue; after the re-link job.
  - Keep the "who writes it" rule: `VenueFoodTopicService` only.
- **`MenuItemFoodTopic`** (`menu_item_food_topics`), or a `topic` column on `MenuItem` if one topic per item is enough. Check `resolveMenuItem`: it returns several, so it's probably a table. Written when the delivery scrape stores items.
- **One re-link job**, `FoodTopicRelinkJob` (`stately`, one `singletonKey`), queued by `FoodTopicService` on any topic or alias change. It re-resolves:
  - mention topics
  - menu item topics
  - feedback point `foodTopic` (from `opinions-table`: if that task added its own job, fold it into this one; if this task lands first, `opinions-table` registers into it)
  - then refreshes venue tags for every city.
  All pure matching, so it needs no LLM. Log its counts.
- **Backfill**: the first run of the job fills everything from stored data.
- **Brand food** (`brandFoods` in `theme-insight.service.ts`: a brand's main food is the primary of most of its places in the city) becomes a query on stored primaries. Keep the rule and move the code.

## Scope
- In: the three link tables or columns, the refresh hooks, the re-link job, moving every reader listed in Why, tests, the skill, `ENTITIES.md`.
- Out:
  - The unrecognised-words list (`FoodTopicService.overview`): it is about text that matches nothing, so it keeps reading raw cuisines and categories.
  - LLM re-reading of cuisines: everything here is pure matching. A mention whose cuisine the LLM left empty stays empty.
  - Exposing food filters on public pages.
