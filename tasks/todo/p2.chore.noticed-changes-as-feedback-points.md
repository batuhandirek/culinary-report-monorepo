# Noticed changes as feedback points

## Goal
`Review.changes` holds `FeedbackPoint[]` (`{ topic, theme, detail }`) rather than `string[]`, with the themes of the shared vocabulary (`price_increase`, `portion_size`, `quality_change`, `ownership_change`, `renovation`, `staff_change`, `space`, `cash_only`, …), so the report's "changes guests noticed" groups "burgers are getting smaller", "burgers are smaller than before" and "made smaller" as portion size, and the lead score's and the city view's "changes" count by theme.

## Why
On dev (2026-10-21) 355 change strings have 324 distinct spellings; the report view groups them by lower-case only. With `feedback-themes` the same phrase is already themed when it is also a complaint, so the change list is the one place left that cannot be summed.

## Design
- `ReviewAnalysisAgent`: `changes: z.array(feedbackPointSchema)` (same `{ theme, detail }`; the topic derived). The instruction keeps the examples.
- `Review.changes` typed `FeedbackPoint[] | null`; migration converts stored strings to `{ topic: 'other', detail }` (no theme), and `FeedbackThemeService.fileThemes` files them like any other unthemed point.
- `ReportReviewStats.changes` becomes `{ stars?, changes: FeedbackPoint[] }[]`; `ReportView` groups by theme with the details under each; the highlights prompt is unchanged in meaning ("one entry per review"). Rebuild stored reports.
- `BrandLeadScoreService` keeps counting reviews with any change.
