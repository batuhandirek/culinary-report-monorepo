# Feedback points table

## Goal
Everything the LLM reads out of a post mention or a review lives in one table, one row per thing said, e.g. `{ source: review #812, theme: price_increase, dish: "cheeseburger", foodTopic: burgers, sentiment: negative, detail: "prices went up" }`. `Review` and `Mention` stay as the raw sources (text, stars, the post, the match), keeping only their overall `sentiment` and `summary`. Every reader (reports, trends, the theme tab, the portal, highlights, the pitch, the lead score) reads the table. A new source (TripAdvisor already lands in `reviews`; later comments or web mentions) only has to write rows.

## Why
- **The same job is done twice.** `Mention` (`social/entities/mention.entity.ts`) and `Review` (`venues/entities/review.entity.ts`) each carry `praise: FeedbackPoint[]`, `complaints: FeedbackPoint[]` and `dishes: FeedbackDish[]` as jsonb (`venues/interfaces/feedback.interface.ts`). About 17 files unpack both and glue them back together. `trends/util/theme-counts.ts`, for example, keeps `THEME_REVIEW_POINTS_SQL` and `THEME_POST_POINTS_SQL` apart and unions them. Each feature rebuilds "what do people say about X" in its own way.
- **Dishes and opinions aren't linked.** "The burger got pricier" is stored as a dish (burger, negative) plus an unrelated complaint (price_increase). On dev, 44 % of review food points name a dish of the same review in their phrase (measured in `feedback-point-dish`), but nothing records the link.
- **Food topics are matched on read.** A dish name reaches `FoodTopic` only through `FoodTopicIndex` at read time (`dishRow` in `trends/util/compute-trends.ts`). "Which opinions are about Burgers" has no join and no index. `TopicInsightService` loads the whole city and filters in code.
- **No single opinion can be corrected.** An admin can't fix one wrong opinion without rewriting the source's jsonb.
- Nothing is released (root `CLAUDE.md`), so shapes change freely with no shims. Only the dev data has to come across.

## Design
This is the shape I'd go with. Where the code says otherwise, follow the code and log why.

**Entity `FeedbackPoint`** (`feedback_points`). It gets its own module `modules/feedback`, with `FeedbackService` as the only writer. The entity replaces the jsonb `FeedbackPoint` and `FeedbackDish` interfaces (`venues/interfaces/feedback.interface.ts`): delete them and repoint their imports at the entity or a DTO. Venues and social import it; it imports neither, since entity references need no module import. The `FEEDBACK_THEMES` vocabulary can stay in `venues/constants/` for this task.
- `review` → `Review` (nullable, cascade) and `mention` → `Mention` (nullable, cascade). Exactly one is set, enforced by a check constraint. Add `sourceKind` (`review` | `mention`) so later sources extend an enum, not the query shape.
- `city` → `City` and `month` (`YYYY-MM`, UTC, from `Review.publishedAt` / the post's date), copied from the source. These never change after the fact.
- **Don't copy brand or venue onto the row.** They change after extraction: matching, `admin-mention-corrections`, branch moves, `BrandAutoMergeJob`. Join through `review.venue.brand` / `mention.brand` / `mention.venue`. For the same reason, don't store "own post": `ownPostSql` decides it at read time.
- `sentiment`: `positive` | `negative` | `mixed` | `neutral` (`FeedbackSentiment`). A praise point becomes `positive`, a complaint `negative`.
- `topic` (the nine `FEEDBACK_TOPICS`) and `theme` (a `FEEDBACK_THEMES` key). `theme` is null only on a dish-only row (below). The topic is still derived from the theme in code (`withTopics`). Store both as plain text, not native Postgres enums. The vocabulary is edited in code, and a native enum would need a migration for every theme added.
- **Vocabulary drift.** The stored `topic` copies a code constant. When a theme moves to another topic or is renamed, the rows keep the old value. `FeedbackService.realign()` sets `topic` from `FEEDBACK_THEMES` for every row and sends rows whose theme no longer exists back to re-filing (theme null, so `fileThemes` picks them up). It runs from the existing backfill route and is cheap. Put the rule in the skill: after editing the vocabulary, run the backfill.
- `dish` (as written), `dishKey` (the `dishRow` rule, so "döner", "doner kebab" and "kebabs" share a key), and `foodTopic` → `FoodTopic` (nullable, set null), resolved when the row is written.
- `detail`: the phrase. Null on a dish-only row.
- `amount` (numeric, nullable) and `unit` (`minutes` | `money`, nullable): the number the opinion states, so "waited 40 min" is `{ theme: wait_for_food, amount: 40, unit: minutes }` and "dürüm now €9.50" is `{ theme: price_increase, amount: 9.5, unit: money }`. Money is in the city's currency (check whether `City` has one; `MenuItem` uses its listing's). Set only when the source states the number, never estimated. "An hour" is 60, "half an hour" 30, and a range ("30 to 40 minutes") stores its upper end. This is what lets a reader answer "how long" and not just "how many".
- Indexes to start from: `(city, month)`, `(foodTopic, month)`, `(review)`, `(mention)`. Add one for theme counts if a plan shows the need.

**Dish-only rows.** A dish in the source's `dishes` list that no point of the source names (same `dishKey`) becomes its own row: `theme` null, `dish` set, the dish's sentiment. This keeps the trends dish table and the report's dish list counting what they count today. Readers count per source, as they do now, so a dish named by a point and also listed once is never counted twice.

**Extraction** (`ReviewAnalysisAgent`, `MentionExtractionAgent`, both via `feedbackPointSchema`):
- A point gets an optional `dish`: the dish or drink it is about, as written in the `dishes` list. It's absent when the point is about the place or the food as a whole. This is the design in `feedback-point-dish`, which this task absorbs.
- A point gets optional `amount` and `unit` (see the entity), and the instruction says in one sentence: only when the text states it.
- `ReviewService.analyse` and `MentionExtractionService` hand points and dishes to `FeedbackService.replaceFor(source, …)` in the same transaction that writes the source. Re-analysing a review replaces its rows.
- **Never re-extract posts to fill the table.** Re-extraction recreates mentions and loses their matches and admin corrections (`feedback-themes` log).

**Writing and re-linking**
- `FeedbackThemeService.fileThemes` and `backfillReviews`, and `MentionExtractionService.backfillThemes`, file themes on rows instead of jsonb.
- When a `FoodTopic` or its aliases change (`FoodTopicService.create` / `update` / `apply` / delete), a pg-boss job re-resolves `foodTopic` for rows with a dish: a `stately` queue with one `singletonKey` (pattern: `BrandAutoMergeJob`, `apps/backend/CLAUDE.md`). Matching is pure code, so a full re-link is cheap. This keeps the "edit an alias and every page updates" behaviour that text matching gives today.

**Backfill and cutover**
1. Add the entity and table. The migration only creates the table: migrations are generated, never hand-edited, so the data move goes in a service method behind an admin route, like `POST /admin/feedback-themes/backfill`. Check the `backend-entity` skill for the house pattern before building it.
2. Fill from jsonb: every praise and complaint point becomes a row, then dish-only rows for the unnamed dishes. Link a point to a dish without an LLM when its detail names exactly one of the source's dish names (same `dishKey`). The rest go to the LLM dish pass (below). Fill `amount` and `unit` for wait and price points by parsing the stored English `detail` ("40 min", "an hour", "€9.50", "9,50 €"), as a pure util with a spec, and log the hit rate. A paraphrased detail may have dropped the number the review gave. Running it a second time does nothing.
3. Move the readers. **The user's call (2026-10-22): anything may break in between, as long as the finished change is complete.** So don't build adapters that rebuild the old `{ praise, complaints, dishes }` shapes. Rewrite each reader, and the pure utils and their specs (`summarizeReport`, `countThemes`, `compute-trends`), against feedback rows directly, wherever that gives the cleaner code. The parity check in Acceptance is the safety net, not a staged cutover. Readers to move (grep `praise|complaints|dishes` on `Mention`/`Review` for the full list):
   - `highlights/util/highlights.ts`, `outreach/services/pitch-hook.service.ts`
   - `portal/services/portal.service.ts`, `portal/util/portal-series.ts`
   - `reports/services/report.service.ts`, `report-signals.service.ts`
   - `reports/util/city-section.ts`, `correlations.ts`, `reach.ts`, `summarize-report.ts`
   - `trends/services/trend.service.ts`, `theme-insight.service.ts`, `topic-insight.service.ts`
   - `trends/util/compute-trends.ts`, `theme-counts.ts`
   - `venues/services/brand-lead-score.service.ts`, `review.service.ts` (its jsonb `@>` filter and `jsonb_array_elements` query), `feedback-theme.service.ts`
   - the review-watch and TripAdvisor paths (their suites mock the agents)
4. Move the API responses and the pages that read these fields live:
   - `social/dto/admin-social.output.dto.ts`: a mention's `praise` / `complaints` / `dishes`, shown on `routes/(admin)/admin/posts/[postId]/+page.svelte`.
   - `venues/dto/admin-venue.output.dto.ts`: a review's, on the admin branch page.
   - `portal/dto/portal.output.dto.ts`: a review's, on the portal's `reviews/components/ReviewCard.svelte`, and a mention's dishes.
   - `portal/dto/portal.input.dto.ts`: the reviews topic filter, today the jsonb `@>` in `review.service.ts`, becomes a join.
   The responses serve `feedback: FeedbackPointDto[]` per review or mention (theme, topic, sentiment, dish, amount, unit, detail), and each page groups them by sentiment. Don't rebuild the old three lists on the server. `portal-series.output.dto.ts` and the trends DTOs are computed shapes, so only their loading moves. Run `npm run create:client` after the DTO change.
   Pages that read saved snapshots (`views/report/*`, `views/highlights/CityHighlightView.svelte`) read `Report.data` / `CityHighlight.data`, not these columns, and stay as they are.
5. Drop `praise`, `complaints` and `dishes` from `Mention` and `Review` once nothing reads them.

**LLM passes over stored points** (the user, 2026-10-22: "LLMs will finish eventually, processing each day"). Both run, and neither re-extracts a source:
- **Dish links**: after the deterministic linking, a mini agent gets each unlinked food or drink point with its source's `dishes` names and picks one or none. Store "looked at, no dish" so a point is asked once.
- **Amounts**: wait and price points still without an amount after parsing go to a mini agent with the source's text, which answers the stated number or none.
Each is a backlog registered with `daily-llm-backlog`, which drains them a little each day within the LLM allowance. If that task hasn't landed, give each pass an admin route that does one batch and reports `remaining`, like `POST /admin/feedback-themes/backfill`, and register them once it lands.

**Untouched:** `Report.data`, `CityHighlight.data` and `FoodTrendsReport.data` are built snapshots and keep their own copies. Rebuilt reports read the table.

## Scope
- In: the entity, the module, both agents' `dish` and amount fields, the writers, the food-topic re-link job, vocabulary realignment, the jsonb backfill, moving every reader, the API responses and the four pages that read these fields live, dropping the jsonb columns, tests, the skill, root `ENTITIES.md`.
- Out:
  - `Review.changes` (free strings). `noticed-changes-as-feedback-points` turns them into themed points; once this lands, they become feedback rows with a flag. Leave it as its own task, but write it against this table.
  - Admin editing of a single opinion: the table makes it possible, not this task.
  - `PostComment` and `WebMention` as sources: their analysis shapes differ (intent, kind), and they're a later decision.
  - Showing anything new in the UI: the city tab's dish breakdown from `feedback-point-dish` becomes one `group by` on this table and can follow as a small task.
  - Embedding clusters (`feedback-theme-discovery`). That task can later read details from this table.
