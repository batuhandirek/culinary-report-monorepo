# Make search by meaning (`like`) find claims inside a filtered scope

## Goal
`like` on `GET /admin/statements` and `GET /admin/explore/claims` returns the claims of the scope closest in meaning, however narrow the filters (a city's month, a brand, a branch). Then the UI can offer "Similar to…" and the groups' "See claims" again.

## Why
Both queries `order by embedding <=> ? limit 50` with the filters in the `where`. Postgres picks the HNSW index (`statements_embedding_hnsw_index`), which hands back its `hnsw.ef_search` (40) nearest claims across every city and month, and the filters then drop them. On dev (2026-11-03), using the vector of "the staff was very friendly" (claim 51231) in Berlin's October: 0 rows, plan `Index Scan using statements_embedding_hnsw_index … Rows Removed by Filter: 47`, though 426 claims saying it have vectors.

## Scope
- In: both `like` paths (`StatementService.list`, `StatementInsightService.claims`). Options: an exact scan over the filtered set (a month is ~20k claims; materialize the filtered rows first so the planner cannot use the index), or pgvector 0.8's `set local hnsw.iterative_scan = strict_order` with a high enough `hnsw.max_scan_tuples` inside a transaction. Exact is simpler and right for an admin search.
- In: putting "Similar to…" back in `ClaimsTable` and "See claims" in `ExploreGroups` / `MissingAspectsView`, once the user has an embeddings client for phrases again (the reason the UI was taken out).
- Out: the clustering (`StatementClusterService`, `AspectDiscoveryService`, Explore groups): they read the vectors without the index.

## Acceptance
- [ ] A PGlite test with more than 40 embedded claims outside the filter and a few inside finds the ones inside, closest first.
- [ ] On dev, `like=the staff was very friendly` with Berlin and October 2026 lists friendly-staff claims first.
