# Key budgets, coverage and the Data page by operation, not by `PipelineStepEnum`

## Goal
An operation (`pipeline/<operation>/`, one workflow per cadence) is the unit everything is keyed by: a city's budgets (`City.stepBudgetsUsd` → per operation and cadence), the Data page's coverage (which run of which operation covered a city and period, read from the run's stored result) and the money page's spend. `PipelineStepEnum`, `STEP_RUNS_IN`, `MONTH_STEPS` and `DEFAULT_STEP_BUDGET_USD` are gone; a workflow's step names are its own words, nothing reads them from outside.

## Why
`PipelineStepEnum` wears three hats: it names an operation (the budget key `stepBudgetUsd(city, PipelineStepEnum.X)`), names a step inside a workflow (`@DurableStep({ name: PipelineStepEnum.X })`) and keys the Data page's lookup (`STEP_RUNS_IN`: which workflow holds which step, or the whole workflow). So a workflow must keep an enum-named step exactly where the Data page expects one (the `SCRAPE_REVIEWS` step is now the TripAdvisor side plus a summary only to keep that contract), the admin's city form lists budgets by step names that no longer match the operations (`SNAPSHOT_RATINGS` is `rating-snapshot.week`, `WATCH_REVIEWS` is `review-watch.week`, `TRACK_DISH_SEARCHES` is `dish-searches.day`), and a new operation touches three constants files and the Data page before it runs. With one id per city and period (`operationRunId`) and every run's result stored by DBOS, the operation's run is the record: the Data page can read it directly.

## Scope
- In: `OperationRun` (`pipeline/shared/util/operations.ts`) becomes the one registry entry: `{ operation, cadence, queue, budgetUsd? (the default), paid: boolean }`, every operation's constants file exporting its runs, a `pipeline/constants/operations.constant.ts` that only lists them (`OPERATIONS: OperationRun[]`, replacing `STEP_RUNS_IN`, `MONTH_STEPS`, `DEFAULT_STEP_BUDGET_USD`); `City.stepBudgetsUsd` → `budgetsUsd: Partial<Record<'<operation>.<cadence>', number>>` with a migration carrying the dev values across (map each enum value to its operation); `stepBudgetUsd(city, step)` → `operationBudgetUsd(city, run)`; `DataCoverageService` reads an operation's run by `operationRunId` (month cadences) or its latest run by attributes (`durable.list({ workflowName, attributes: { cityId } })`), and shows the run's status and stored result instead of a step attempt; the admin city form's budget rows listed from `OPERATIONS` (label = `operation.cadence`); `withLlmCallContext`'s `pipeline:<STEP>` purposes → the operation's name; `@DurableStep({ name: PipelineStepEnum.X })` → plain names (`save venues`, `tripadvisor`); the `STEP_RUNS_IN` and `PipelineStepEnum` references in the skills and `operations.md` (§3's "step" column becomes the workflow's real steps).
- In: the frontend's `CityOverviewTab` / `CityFormDialog` budget editing and whatever the Data page component reads (`npm run create:client` after the DTO change).
- Out: changing what any operation does or spends; the money page's grouping by purpose (the ledger's `purpose` strings change name only).
