# Daily LLM backlog

## Goal
Backfill work that needs an LLM (filing themes, linking feedback to dishes, reading amounts, anything later) is a list of registered backlogs. A daily cron works through them in priority order until the day's budget is spent or the provider's allowance runs out, then stops cleanly and continues the next day. The Data page shows each backlog's remaining count and when it last moved. Nobody calls an admin route "until `remaining` is zero" by hand.

## Why
- Every backfill today is an admin route someone calls repeatedly: `POST /admin/feedback-themes/backfill` (`social/controllers/admin.feedback-themes.controller.ts`) and the opening flags route (`admin.opening-flags.controller.ts`, "call again with…"). Each new linking task adds another.
- The mini model has a free daily allowance per account (`OpenAIAccountsService`: "the daily complimentary allowance is per model"; `review-analysis.agent.ts`: 10M tokens a day). A daily drain uses it for free instead of in bursts that hit the limit.
- The linking tasks (`opinions-table`, `food-topic-links`) each have an LLM pass over stored data. The user's call is that these finish over days, not in one run.

## Design
- **The interface**, in `modules/llm` or a small `modules/backlog`: `LlmBacklog { key; label; priority; remaining(): Promise<number>; runBatch(): Promise<{ done: number; tokens?: number }> }`. Each owning service registers its own backlog at module init, so the cron never imports the domain modules and the owner stays the only writer.
- **The cron**: daily at a quiet hour, away from `MonthlyPipelineCron` and `WeeklyListeningCron` (check their times), as a pg-boss `stately` job with one `singletonKey`, so a slow day never overlaps the next.
  - It takes backlogs by priority and calls `runBatch` until the backlog is empty, the day's budget is spent, or a batch throws the error `isFatalProviderError` recognises (every account out of allowance). It then stops without failing.
  - The day's budget is a config value (`LLM_BACKLOG_DAILY_TOKENS`, default well under the 10M allowance, leaving room for the pipeline's own extraction and analysis). Pipeline work always comes first.
- **Records**: a `BacklogRun` row per backlog per day (key, date, batches, done, tokens if known, stop reason: `empty` | `budget` | `allowance` | `error`), so the page can show progress and a backlog stuck on errors is visible.
- **Admin**: on the Data page (`admin-ui` skill, the Runs tab is the natural home), each backlog with its remaining count, done in the last 7 days, last stop reason, and a "Run now" button that queues the job.
- **Backlogs at launch:**
  - Feedback themes: the existing `FeedbackThemeService.fileThemes` path for reviews and mentions. The admin route stays for now, but the cron is the normal way.
  - Feedback dish links and feedback amounts: from `opinions-table`, registered by `FeedbackService` once that lands.
  - Anything later registers the same way. The skill says so.
- **Never in a backlog:** re-extracting posts (recreates mentions and loses matches and admin corrections), or anything that costs per call beyond the allowance (Apify, paid models). The interface comment says so.

## Scope
- In: the interface, the cron, the run records, the Data page section, moving the theme backfill onto it, tests, the skill.
- Out: the pipeline's own LLM steps (`EXTRACT_MENTIONS`, `ANALYSE_REVIEWS`, …), which stay in the pipeline. Token metering per call, if the agents don't already report usage: log batches and items, and record tokens only where the agent result gives them.
